How it is built

Architecture

Three layers, and each knows nothing about the one above it. That is why the git core can be tested without a window, and why a screen that looks broken is almost always a store bug rather than a Rust one.

The three layers#

src/ — SvelteKit, SPA mode#

One store per screen. The only module that crosses into the backend is src/lib/api.ts.

↓ invoke

src-tauri/ — the Tauri shell#

Commands, background workers, the filesystem watcher, and the window. No git logic.

↓ calls

crates/spagitty-core — git#

Every git operation, through gix for reads and the git binary for writes. No Tauri types.

crates/spagitty-farm — agents#

The farm's control plane. Orchestrates and nothing else — and calls spagitty-core for every git operation rather than reimplementing one.

src/                      SvelteKit SPA. One store per screen.
  └── invoke ───────────► src-tauri/           Tauri commands, worker, watcher.
                            ├── calls ───────► crates/spagitty-core/   Git, via gix + git.
                            └── calls ───────► crates/spagitty-farm/   Orchestration: agents,
                                                                       worktrees, verification,
                                                                       review — and it calls
                                                                       spagitty-core for git.

The rules that hold the seams#

Four rules, each load-bearing

Only src/lib/api.ts calls invoke. A command rename is a one-file change.
spagitty-core never imports Tauri. No window handles, no events, no app state — so it compiles and is tested without a GUI.
Only shell.rs spawns a process. One place knows what was executed.
Only forge/http.rs makes a network request. One place knows what was sent.

Crossing the boundary#

Types that cross to the frontend derive Serialize with #[serde(rename_all = "camelCase")], and are mirrored by hand in src/lib/types.ts. The two are kept in step deliberately rather than generated, because the wire shape is small and a generator would be more machinery than the problem needs.

Errors cross as plain strings. Error's Display text is therefore user-facing — plain, specific, no stack-trace jargon — and screens show that string directly rather than substituting a message of their own.

Every command and every event is catalogued on the IPC reference.

The git binary boundary#

The rule, in one sentence:

If the operation mutates state that the wider git ecosystem also reads, or delegates to something outside the repository, it shells out to git. Read-only history questions are answered in-process with gix.

In-process, with gixThrough the git binary
Log walking, refs, diffing, status, the index's conflict stages, stash entries read from the reflog, tags, remotes as configured, identity as resolved Committing, staging, checkout, stash push, interactive rebase execution, hooks, LFS, submodule recursion, credential helpers, writing git config, cloning, and every operation in ops.rs

The table in shell.rs's own header is the authority and is extended in the same change that adds an operation to it. gix is MIT/Apache-2.0, which links cleanly into a GPL-3 program.

One read breaks the rule, and it is written down rather than quietly done — blame. The reason, and its end condition, are on the core crate page.

The one function that does not wait#

shell::clone_start is the only spawn that does not wait for git to finish: a clone runs for minutes, reports progress as it goes, and has to be cancellable, so the caller owns the child process. Everything else in the module is a command that ends.

What ran, recorded at the boundary#

Because there is one module that spawns, there is one place that knows what was executed. record.rs holds it: a process-wide ring buffer of the last 200 executions, written by shell.rs itself as each command finishes — argv, outcome, exit code, duration.

That location is the whole point of the feature. A screen composing its own “the command behind this button” string would be describing what it asked for: it would not know that a fetch carries --prune --progress, that a force push is --force-with-lease, or that reverting a merge gained -m 1 on the way down. The record is written where the process is started, so it is evidence rather than a claim, and every spawn goes through the same two functions so a new one cannot quietly skip it.

  • Reads are absent, deliberately. Log walking, refs, diff and status are in-process and have no command line. Nothing is synthesised for them, and the panel says so.
  • Credentials are removed on the way in, not on the way out. A clone URL's userinfo is stripped before the entry is stored.

The network boundary#

forge/ is as narrow as shell.rs's boundary and for the same reason.

  • forge/http.rsThe only file that may construct or use the HTTP client.
  • forge/github.rsOne GraphQL request per refresh — REST would need 1 + 3N calls for the same rows.
  • forge/gitlab.rsGitLab merge requests, mapped onto the same contract.
  • forge/bitbucket.rsBitbucket Cloud pull requests, same contract.
  • forge/review.rsA pull request's files, and the review somebody leaves on it.
  • forge/keychain.rsThe personal access token, in the OS keychain and never in a configuration file.

Two things the layers share#

The row pitch is defined twice on purpose#

Lane elbows are described in row units in crates/spagitty-core/src/graph.rs; the stylesheet needs the same number in CSS pixels from src/lib/metrics.ts, which is the source of truth. Rather than let them drift, the frontend fetches the Rust value at boot through the metrics command and logs an error if they disagree — and a Rust test reads the TypeScript file and fails with both values named if the constants ever move apart.

Structural numbers live in one file#

src/lib/metrics.ts publishes them as CSS custom properties. There is no height: 26px in any component, and no second 26 anywhere in the frontend.

Data flow: opening a repository#

  1. repo.open(path) calls the open_repo command.
  2. Rust opens the repository, builds the ref index, computes the cheap counts, spawns a graph worker and a filesystem watcher, and returns { info, counts, token }.
  3. The worker walks nothing yet. The graph store asks for rows with graph_request(token, count).
  4. Rows arrive as graph-rows events in batches; graph-done ends the walk.
  5. Rows carrying a token other than the current one are dropped. That is how a superseded walk is discarded without cancellation races.
  6. The watcher emits repo-changed. Refs moving debounces into a re-read and a re-walk; a worktree change re-reads the counts only.
Why visibility is a root set, not a filter

Hide, solo, smart visibility and pin-to-left all resolve to a root set for a fresh walk rather than to a filter over rows the frontend already has. Filtering client-side would leave the lanes drawing edges between commits that are no longer parent and child.

Concurrency#

Nothing polls. Long work runs on a thread that owns its own cancellation, and the webview is told what changed.

WorkerShape
GraphOne thread per open repository. Walks history and emits batches.
SearchOne thread per query. Starting one cancels the one before, and rows carrying a stale token are dropped.
CloneOne thread per clone, owning the git process — so cancelling is a signal rather than a request.
NetworkFetch and push, watched while they run rather than fire-and-wait.
RebaseOne thread, watching git rewrite history, with progress read from git's own state counters.
Watchernotify over the git directory, debounced.
FarmOne thread per running agent, with a process group (or a Windows job object) so stopping stops descendants too.

The farm's Tauri commands are #[tauri::command(async)] rather than plain, because they take locks that agent threads hold — and a blocking command runs on the thread that paints the window.

Platform facts, arranged before the window#

platform.rs is the other file that is not about git at all. It arranges the webview's environment as the first statement of run — before the builder, and while the process is still single-threaded, which is the only state in which setting an environment variable is sound.

It sets WEBKIT_FORCE_COMPOSITING_MODE=1, keeping the whole page on the GPU rather than letting WebKitGTK fall back to software for the parts its heuristics misjudge. It deliberately does not set WEBKIT_DISABLE_DMABUF_RENDERER, and that is a reversal of an earlier decision — the reasoning is on the Tauri layer.

Branching and releases#

Git Flow: main and dev are protected, and work happens on feature/, task/, bugfix/, hotfix/ and release/ branches named after their work item. A pull request is the only path into a protected branch. CI is six ordered gates — see CI/CD & releases.
