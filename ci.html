How we work

CI/CD & releases

The pipeline is a sequence of gates in a fixed order. A gate that fails stops the pipeline; nothing downstream runs. Cheapest and most certain first, so an obvious failure never burns a full three-platform build.

The gates#

#GateRunsProves
0Scope A diff of the push or pull request against the previous tip Whether the change ships in the application. Gates 5 and 6 read this; documentation alone is not a release.
1License cargo deny check licenses bans sources, a licence check over the JS production tree, plus a check that the licence files and both manifests still say GPL-3.0-or-later Every dependency's licence is identified and permitted, and nothing conflicts with shipping under GPL-3.
2Code quality cargo fmt --all --check, cargo clippy --workspace --all-targets -- -D warnings, bun run check, plus the brand and icon generators in --check mode Formatting, lints and types across both languages, and no drift between the brand generators and the committed art.
3Tests and coverage cargo llvm-cov --workspace --fail-under-lines 70, bun run coverage The suite passes and first-party coverage holds its floor: 70% for Rust, 65% branches for the frontend.
4Security cargo deny check advisories, bun audit --audit-level=high, gitleaks over the diff No known-vulnerable dependency at high or above, and no secret in the change.
5Build bun run tauri build on Linux, macOS and Windows — main, shipping changes only The release build works on every target, not only the one the author uses.
6Release Tag, artifacts, and notes read from CHANGELOG.md — main, shipping changes only The build is published, carries its changelog section as notes, and is traceable to a commit.

What runs where#

BranchWhat happens
main Gates 1 to 4 on every push. Gates 5 and 6 run only when the change ships — something under src/, src-tauri/, crates/, or a version, lockfile or frontend config the built application depends on. Passing gate 6 publishes the release. A README, docs, working-record or brand-collateral edit is not a publish: those land without rebuilding three platforms or tagging, and ride the next version. The scope job makes that call.
dev Gates 1 to 4, automatically, then the pipeline stops. Building and publishing an alpha from dev is a manual action: run the prerelease workflow and give it an alpha number. It produces vX.Y.Z-alpha.N, which is never a release of main.
Pull requests Gates 1 to 4, into either branch. Since a pull request is the only path into a protected branch, that is where the results are read.

Every lane builds all three platforms#

Gate 5 and the prerelease workflow each run on Linux, macOS and Windows runners; the draft workflow builds Linux, Windows, and macOS on two runners — Apple silicon and Intel — since a build made on one does not run on the other. Gate 5's macOS build is Apple silicon only, so a published release currently has no Intel Mac download. That is recorded as an open question rather than fixed unwatched on the blocking release path.

Nothing is signed

There is no Apple Developer account and no code-signing certificate in this project, so macOS Gatekeeper refuses a downloaded build on a double-click and Windows SmartScreen warns. The draft lane's release notes carry the one step a Mac user needs. Adding real signing is a change to gate 5 and the draft lane together, not to one of them.

The rules#

  • Gates are blocking, not advisory. A red gate is fixed, not bypassed. continue-on-error is not used to get a merge through, and neither is a re-run until it passes.
  • An advisory that cannot be fixed is recorded, not silenced. The [advisories] ignore list carries accepted risk by advisory id, each with its crate and its reason, so anything not listed still fails gate 4. That is the line between recording a risk and switching the gate off, and only the first is allowed. A blanket setting — unmaintained = "warn", or dropping the check — is the second wearing different clothes.

    Sixteen entries are listed today, all unmaintained, none a vulnerability, and eleven of them the GTK3 bindings Tauri links against on Linux with no upgrade available. They are deleted when Tauri moves to GTK4.
  • The order is fixed. A new check joins an existing gate or becomes a new one in the right place — it does not get bolted onto whichever job is convenient.
  • The coverage floor is defined once per language, and the two are not the same number.
  • Tags are never moved. Gate 6 refuses to publish over a tag that already exists and tells you to bump the version instead.

Release notes come from the changelog#

A version's section in CHANGELOG.md becomes that version's release notes verbatim. Gate 6 reads it and refuses to release without one, so a changelog entry is written into ## [Unreleased] in the same change as the work it describes rather than reconstructed afterwards from commit messages.

The format follows Keep a Changelog; versions follow Semantic Versioning. Spagitty is at 0.x: the surface is not stable, MINOR may break, PATCH stays backward-compatible.

The three release lanes#

LaneTriggered byProduces
ReleaseA shipping merge into mainvX.Y.Z, tagged, with installers for three platforms and the changelog section as notes.
PrereleaseRun by hand from dev, given an alpha numbervX.Y.Z-alpha.N. Never a release of main.
DraftRun by handA draft release, including an Intel macOS build, for checking artifacts before they are public.

Running the gates locally#

Gates 1 to 3 are what a change is checked against before it is committed.

bun install --frozen-lockfile              # the dependencies, locked
cargo deny check licenses bans sources     # gate 1
cargo fmt --all --check                    # gate 2
cargo clippy --workspace --all-targets -- -D warnings
bun run check
python3 tools/make-icons.py --check        # gate 2 — brand drift
python3 tools/make-brand.py --check
cargo llvm-cov --workspace \
  --ignore-filename-regex '(fixture|testing)\.rs' --summary-only
bun run coverage                           # gate 3
cargo deny check advisories                # gate 4
bun audit --audit-level=high
cargo install cargo-deny cargo-llvm-cov
One difference between local and the runner

gitleaks walks the pull request's merge ref on CI and the branch tip locally, so the commit counts differ. Both scan everything they are given.

Candidate gates, not adopted#

Recorded as proposals. None is in force:

  • Supply-chain provenance at release — an SBOM and signed artifacts, between gates 5 and 6.
  • Artifact smoke test — launch the built application and perform one core operation, after gate 5. It catches the class of failure where everything compiles, every test passes, and the packaged app is broken.
  • Working-record compliance — verify a branch name carries a valid work item id and that its documents exist. Would sit at gate 0; costs nothing.
  • Commit and PR hygiene — conventional-commit linting. Its original payoff, reliable generated notes, lapsed when gate 6 moved onto the changelog, but tidy history remains its own argument.

The cross-platform build matrix was also a candidate. It is adopted, and is what gate 5 already does.
