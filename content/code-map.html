Where to start reading

If you want to understand…Read, in this order
How a screen gets its data src/lib/<screen>/store.svelte.ts → src/lib/api.ts → src-tauri/src/commands.rs → the core module it forwards to
How git is actually performed crates/spagitty-core/src/lib.rs → shell.rs's header (the boundary table) → the module for the operation
How the graph is drawn crates/spagitty-core/src/graph.rs → src/lib/graph/store.svelte.ts → lanes.ts → LaneCanvas.svelte
How the farm decides anything crates/spagitty-farm/src/lib.rs → model/ → orchestrator/scheduler.rs (a pure function) → service.rs
Why a decision was made The module's own header comment first — they carry the reasoning — then the work item under agile/items/

crates/spagitty-core — git

No Tauri types, no window handles, no events. It compiles and is tested without a GUI, and its examples run it from a terminal. Full detail: spagitty-core.

  • repo.rsOpening a repository, describing it, reading HEAD.
  • graph.rsThe log walk, lane assignment, lane colours, edges, the row pitch.
  • refs.rsThe ref index — commit id to the refs pointing at it, built once per refresh.
  • branches.rsBranch rows: drift, upstream, merged; checkout and create.
  • diff.rsCommit detail, per-commit file lists, per-file hunks — three levels, because they cost different amounts.
  • conflicts.rsIndex stages 1/2/3 of a conflicted path, and what operation is in progress.
  • rebase.rsThe interactive-rebase todo list, its preview, and its execution.
  • ops.rsEvery git operation that writes — thin, named wrappers over shell.
  • shell.rsThe one place a git subprocess is spawned. Its header carries the boundary table.
  • search.rsThe filtered history walk behind Log search.
  • blame.rsWho last touched each line — the one read that goes through git.
  • stash.rsStash entries, read from the reflog of refs/stash.
  • status.rsThe working-copy status walk, and the counts the nav rail shows.
  • work.rsChanging the working copy: stage, unstage, commit.
  • identity.rsuser.name and user.email per scope — read with gix, written with git config.
  • signing.rsWhether git will sign this commit and whether it can.
  • clone.rsWhere a clone will land, what is wrong with that, and what git's progress output means.
  • remotes.rsAdd, rename, remove, retarget — each through git remote rather than a config edit.
  • reflog.rsWhere a ref has been, and the three ways back to a point in it.
  • tags.rsAnnotated and lightweight told apart, because the difference decides whether a message can exist.
  • worktrees.rsList, add, remove, lock, unlock, prune — parsed from git's --porcelain stream.
  • submodules.rsStatus, recursive init and update, URL sync, deinit.
  • tools.rsExternal diff and merge tools: discovery on PATH, and git's own diff.tool / merge.tool keys.
  • record.rsWhat Spagitty actually ran — the buffer behind the command drawer, written by shell.rs.
  • update.rsWhether there is a newer Spagitty than this one.
  • forge/The only part of the workspace that reaches a network. Six files, one of which may hold the client.
  • error.rsError, whose Display text is user-facing.
  • fixture.rsReal repositories for tests, behind the fixture feature. Excluded from coverage.

crates/spagitty-farm — agents

Full detail: spagitty-farm.

  • model/Farm, Goal, Task, AgentDefinition, AgentRun, Handoff, FarmEvent — the data, and the status machine no path may skip.
  • agent/One adapter per provider, detection on PATH, and the per-repository registry.
  • workspace/A branch and a worktree per task, the leases that stop two agents touching one path, and the sweep for what is left behind.
  • execution/Starting an agent, reading it, stopping its whole process group; the transcript on disk; the narrator.
  • orchestrator/The dependency graph, the scheduler (a pure function), the router, and the planner.
  • verification/The repository's own commands, run in the task's worktree.
  • review/A second agent reading the first one's change, and the decision it returns.
  • persistence/The farm on disk: JSON under .spagitty/, written by rename, events appended one object per line.
  • policy.rsThe repository's AGENTS.md and its neighbours, attached to every prompt.
  • context.rsWhat an agent is told, and the rule that decides it.
  • service.rsThe API, and the only module that changes anything.

src-tauri — the shell

Deliberately thin. Full detail: the Tauri layer.

  • commands.rsOne #[tauri::command] per operation. No git logic.
  • farm.rsThe farm's commands and its event bridge, with a lifetime of its own.
  • graph_worker.rsA thread that walks history and emits batches.
  • search_worker.rsA thread per query; starting one cancels the one before.
  • clone_worker.rsA thread per clone; it owns the git process, so cancelling is a signal rather than a request.
  • network_worker.rsFetch and push, watched while they run.
  • rebase_worker.rsOne thread, watching git rewrite history.
  • watch.rsFilesystem watcher over the git directory. Spagitty does not poll.
  • command_log.rsForwards each recorded execution to the webview as an event.
  • recents.rsThe repositories the user has opened — application state, not git state.
  • settings.rsSpagitty's own behaviour toggles, stored beside the repository list.
  • accounts.rsWhich hosting accounts are connected. A host and a login; the token is elsewhere.
  • profiles.rsNamed identity profiles.
  • about.rsBuild identity, and the dependency licence list generated at build time.
  • platform.rsHost facts that must be true before the webview starts.
  • testing.rsScaffolding for this crate's own tests — a mock app, an event collector, a deadline on a drop.
  • lib.rsCommand registration.

src — the interface

Full detail: the frontend.

Shared, at the top of src/lib/

  • api.tsThe only module that calls invoke.
  • types.tsThe wire types, mirroring the Rust serde shapes by hand.
  • metrics.tsStructural numbers, published as CSS custom properties. The single source of truth.
  • nav.tsThe rail: screen codes, order, labels, counts.
  • repo.svelte.tsThe open repository — which one, what HEAD is, and the rail counts.
  • workspace.svelte.tsRepository tabs, including tabs onto linked worktrees.
  • session.tsWhat a launch resumes, as a sequence a test can watch.
  • themes.ts · theme.svelte.tsThe palettes as data, and which one is on.
  • scale.svelte.tsText size and interface zoom — two independent dials.
  • panels.svelte.tsThe resizable-panel registry: variable, anchored edge, range.
  • format.ts · version.tsRelative times and the build's own version.

The shared frame and kit

  • chrome/Title bar, toolbar, nav rail, repository tabs, status strip, resize edges.
  • ui/What more than one screen needs: Menu, Dialog, Notice, Splitter, Chip, Icon, the column machinery, the glass maps.
  • palette/The command palette — a registry, not a list.
  • commandlog/The drawer of what Spagitty actually ran.
  • network/Fetch and push while they are happening.
  • remotes/ · profiles/ · worktrees/ · submodules/Features that live in Settings or a modal rather than on a screen of their own.

Everything else

  • agile/The working record: 136 items, their plans and their test sweeps. A test fails if the index and the tree disagree. See how we work.
  • docs/The in-repository documentation this wiki is built from — architecture, screens, testing, CI, branding, and the gap analysis the later screens came out of.
  • assets/brand/The master mark.svg and everything generated from it. See brand & identity.
  • tools/The brand and icon generators, the release-notes reader gate 6 uses, and the tests that keep the working record honest.
  • deny.tomlLicence policy, banned crates, and accepted advisories recorded by id with a reason each.
