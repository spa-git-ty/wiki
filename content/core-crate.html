How it is built

spagitty-core

Every git operation Spagitty performs. UI-agnostic: no Tauri, no window handles, no events — so the crate compiles and is tested without a GUI, and its examples run it from a terminal. 

cargo run -p spagitty-core --example graph-dump -- /path/to/repo
cargo run -p spagitty-core --example diff-dump  -- /path/to/repo

The git binary boundary

shell.rs is the only module in the workspace that spawns a process. The rule:

If the operation mutates state that the wider git ecosystem also reads, or delegates to something outside the repository, it shells out to git. Read-only history questions are answered in-process with gix.

So reads — log walking, refs, diffing, status, the index's conflict stages — are gix. Interactive rebase execution, hooks, LFS, submodule recursion, credential helpers, committing, staging, checkout, stash push, writing git config and cloning are git. The table in that module's header is the authority, and it is extended in the same change that adds an operation to it.

gix is MIT/Apache-2.0, which links cleanly into a GPL-3 program.

The one read that breaks the rule

shell::blame shells out, and it is written down rather than quietly done. gix::blame 0.16 — the newest published version — panics on an ordinary history shape: a file blamed at a merge commit whose history contains an intervening commit that left the file alone. Every diff algorithm and both rename settings do it. The exception carries an end condition: blame moves back in-process when the upstream defect is fixed. It is the only read in the workspace that spawns a process.

The one spawn that does not wait

shell::clone_start. A clone runs for minutes, reports progress as it goes, and has to be cancellable, so the caller owns the child process. Everything else in the module is a command that ends.

Reading a repository

  • repo.rs Opening a repository and describing it. open, open_sync, summary, workdir, info, last_fetched, head. RepoSummary is what the All repositories screen reads for a card without opening the repository as the current one.
  • graph.rs History walking and lane assignment. walk, walk_pinned, all_tips, tips_for. Carries ROW_PITCH — the constant duplicated across the language boundary on purpose, with a test that reads the TypeScript file and fails with both values named if they drift — plus LaneEdge, GraphRow, RowLanes and the batch size the worker emits in.
  • refs.rs RefIndex — commit id to the refs pointing at it, built once per refresh and handed to the walk, so attaching chips to a row is a hash lookup rather than a ref scan per commit.
  • status.rs The working-copy status walk and the counts the nav rail shows. Only the counts whose screens exist are computed for real; the rest are None, and the rail renders · rather than a number that would be wrong.
  • search.rs Finding commits. The same revision walk the graph does, with a predicate and without lanes — not a second traversal of history. Query, SearchRow, walk.
  • blame.rs Who last touched each line, parsed from git blame --line-porcelain, plus the file history walk behind screen 1O. What this module owns is the part git does not do: deciding what is worth blaming at all. NotBlamable distinguishes a binary file, a missing path and a directory — an empty list would read as a file nobody has ever touched.

Diffs

  • diff.rs Three levels, because they cost different amounts: commit_detail (the message and the people), commit_diff (the file list and its totals), file_diff (one file's hunks). Also the working-copy variants, the hunk patch a stage-hunk needs, and binary_file_diff / binary_working_diff, which report a size delta and a MIME type rather than pretending a binary has lines.

Writing

  • work.rs Changing the working copy: stage, unstage, stage_hunk, unstage_hunk, discard, discard_hunk, commit. Reading the working copy lives in status.rs; this is the writing half, and every operation goes through shell.
  • ops.rs Every history operation the graph offers: reset, revert, cherry_pick, integrate (merge / rebase / fast-forward, as one Integration enum), rebase_onto, the interactive-rebase lifecycle, checkout_detached, branch rename and delete, tag create and delete, the stash actions, fetch, pull and push. Each is a thin, named wrapper over shell — the naming is the point, because reset(Hard) reads at the call site and --hard does not.
  • shell.rs The boundary itself. Around sixty functions, each one a git invocation, each one recorded as it finishes. ResetMode and PullMode live here because they are the shapes of git's own flags.

Branches, tags, stashes, the reflog

  • branches.rs BranchRow, list, divergences, checkout, create. Ahead and behind are counted against the remote-tracking ref on disk, which is whatever the last fetch left there: nothing here talks to a network, so the numbers are exact for what is known locally and cannot be more current than that — and the screen says so rather than implying it is live. The list re-opens the repository rather than reusing the session handle, because gix reads config once at open time and a branch's upstream lives in config.
  • tags.rs tags, create, delete, retag. Annotated and lightweight are told apart throughout, because that difference decides whether a message can exist at all.
  • stash.rs A stash is not a special kind of object: it is a commit whose first parent is the commit the work was made on, and refs/stash is an ordinary ref whose reflog is the list. push refuses the nothing-to-save case with a reason, because succeeding quietly reads from a button as a stash that happened and then vanished.
  • reflog.rs Where a ref has been. logged_refs, reflog, and the three ways back to a point in it.
  • worktrees.rs List, add, remove, lock, unlock, prune — parsing git's --porcelain stream, with the parser exposed so it can be tested against captured output rather than a live repository.
  • submodules.rs Status, recursive init and update, URL sync, deinit — same shape, same testable parser.

Rewriting and repairing

  • rebase.rs Planning a history rewrite. todo generates the list rather than parsing the file git rebase -i would open — running that would start a rebase, which is the thing the screen exists to avoid — and there is a test comparing it against git rev-list --reverse --no-merges. plan folds an edit list into a Preview; progress reads git's own state counters while a rebase runs, rather than parsing its output.
  • conflicts.rs A repository stopped mid-operation. ConflictKind is derived from which index stages exist — no stage 1 means both sides added the path, a missing stage 2 or 3 means that side deleted it. operation reads what is in progress from the repository's own state, never inferring it from the presence of conflicts, because merge, rebase, cherry-pick and revert all leave conflicts behind and naming the wrong one sends someone to the wrong command. regions, take, resolve_region, write_merged and mark_resolved are the write half; a test asserts that reading never touches the index.

Configuration and identity

  • identity.rs Reading is a gix question — git's configuration cascade, resolved the way git resolves it. Writing goes through the git binary. Origin is what makes the screen honest: a value coming from the system configuration or the environment is named as such rather than as a scope Spagitty writes. IdentityProfile and apply_profile are the named-profiles feature.
  • signing.rs commit.gpgsign is the authority, never a preference of Spagitty's. Problem is the difference between “git will not sign” and “git cannot sign”, which are different things to tell someone.
  • remotes.rs Add, rename, remove, retarget — each through git remote rather than a config edit, so git's own bookkeeping (refspecs, tracking refs) stays correct.
  • tools.rs External diff and merge tools: discovery on PATH, reading and writing git's own diff.tool and merge.tool keys, and launching them.

Bringing a repository in

  • clone.rs Two pure things and no process: where a URL and a parent directory say the clone will land, and what git's progress output means. Problem enumerates everything that can be refused before the process starts. Progress parses git clone --progress, which writes each phase to stderr terminated by a carriage return rather than a newline — and a line it does not recognise is still shown, so a format change degrades to “no percentage” rather than “no progress”.

The forge — the network boundary

This is the only part of Spagitty that talks to a network, and it is as narrow as the process boundary and for the same reason: so that “what does this application send, and where” has one answer.

  • forge.rsThe host-agnostic contract the Pull requests screen was designed against, before any host could be reached.
  • forge/http.rsThe only file that may construct or use the HTTP client. Exactly one, ureq, declared only in this crate.
  • forge/github.rsOne GraphQL request per refresh. REST would need a list call plus three per pull request for line counts, review decision and checks — ninety-one requests for thirty open ones.
  • forge/gitlab.rsGitLab merge requests, mapped onto the same contract.
  • forge/bitbucket.rsBitbucket Cloud pull requests, same contract.
  • forge/review.rsA pull request's files, and the review somebody leaves on it — REST here, with the reason written down where it departs from the list's GraphQL.
  • forge/keychain.rsThe token, in the OS keychain and never in a configuration file.

Supporting

  • record.rs What Spagitty actually ran: a process-wide ring buffer of the last 200 executions, written by shell.rs as each command finishes. redact strips a URL's userinfo on the way in, so an entry that never held a token cannot leak one through the copy button.
  • update.rs Whether there is a newer Spagitty than this one, and what it sends to find out — which is a release listing request and nothing else.
  • error.rs Error. Its Display text crosses into JavaScript as a plain string and is shown to the user directly, so it is written in the same register as the rest of the interface: plain, specific, no stack-trace jargon.
  • fixture.rs Real repositories for tests, built with the git binary — not with gix, because a fixture built by the library under test would agree with it by construction. Published behind a fixture feature so the Tauri layer can walk one too, and excluded from coverage. A release build carries neither the fixtures nor tempfile.
