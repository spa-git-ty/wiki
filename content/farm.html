Using Spagitty

The agent farm

Set a goal. Cut it into tasks. Watch several agents work them at once, on branches you can read in the graph you already trust. The farm is Spagitty's own subject — everything else in the application is where its output is read.

Three rules the whole feature is built around

An agent saying “done” is not done. There is no transition from an agent's own report to Done: verification and a review by a different agent are in the path and cannot be skipped.
Agents never talk to each other. Every handoff goes through Spagitty, so there is one audit trail and one place that decides what happens next.
Nothing an agent does reaches your checkout. Every task runs in its own worktree on its own branch.

Agents, not models

Spagitty runs agents; it does not contain them. There is no model here and no key. Claude Code, Codex, Cursor and Oh My Pi are detected on your PATH, and anything else with a command line can be added by hand. They run as you, with your credentials, on your machine.

ProviderHow it is invokedWhy that form
Claude Codeclaude -p <prompt>Print mode runs the whole turn to completion with no terminal attached and writes the transcript to standard output.
Codexcodex exec <prompt>exec is the non-interactive subcommand: it runs the turn and exits. Bare codex would open a session.

Detection walks PATH itself rather than shelling out to which, and the registry keeps two things apart on purpose: what this machine has, and what you have said about it — the role you want an agent to play, whether it is enabled, and any argument overrides.

The loop

  1. A goal. One sentence, plus any constraints you want honoured. It lives longer than a single run.
  2. A plan. An agent turns the goal into tasks. They arrive as drafts, so a person reads a decomposition before several agents act on it. A band above the list says how many were proposed, with a checkbox each: add them all, add the ones you want, or discard.
  3. Assignment. The router maps a task's kind to a preferred role, the registry finds an agent for that role, and if nobody holds it the task goes to whoever can code.
  4. Work. The task gets a branch and a worktree of its own; the agent runs there, and what it says is narrated into lines a person can watch.
  5. Verification. Your repository's own commands, run in that worktree, stopping at the first failure.
  6. Review. A second agent — never the one that wrote the change — reads it and returns a decision.
  7. Merge. Depending on where you have put the autonomy dial, either you merge it or the farm does.

Where you stand

Five autonomy levels. The setting is a sentence about where you are, not a slider labelled “risk”.

LevelWhat happens
ManualSpagitty organises the tasks. Nothing runs by itself.
AssistedAgents run; you approve every task. This is the default.
Semi-automaticAgents run and review each other; you approve the merges.
AutomaticVerified low-risk tasks may merge themselves.
UnattendedEverything, without you.
Even at the top of the dial

An automatic merge still requires passing checks, a successful independent review of the work actually committed, and merge permission. Competing farm merges serialise rather than racing, and a task keeps its intended destination.

A task

A task is machine-readable on purpose: the farm never relies entirely on free-form prose. It carries a kind, its dependencies, the files it expects to touch, its own verification commands, and the record of every run against it.

Kinds

Architecture, Backend, Frontend, Testing, Documentation, Research, Review, Integration, General. The kind is what routes the task to a role — architect, backend, frontend, tester, reviewer, researcher, or general.

Who asked for it

A farm mixes work you decided on with work a model produced, and after twenty tasks they look identical. Your own tasks stay unmarked; anything an agent asked for carries one quiet mark, and its panel says which agent and why — cut out of the goal, cut out of another task, or proposed while working on something else and asked for by nobody.

Tasks that turn out to be too big

Break it down asks an agent to cut one task into smaller ones. They arrive as a proposed plan under it, and the task becomes a heading that finishes when they do. Deleting the heading keeps the work that was under it.

A branch and a worktree per task

Named spagitty-farm/<task>/<provider> — for example spagitty-farm/TASK-0042/claude. The name is derived, never chosen, and derived in exactly one place, because it is how the commit graph, the worktree list and the Farm screen find each other. A glob over that prefix cleans up a whole farm without touching anything you named yourself.

Two agents in two worktrees cannot corrupt each other's files — that is what the worktrees are for. What they can do is both edit the same path and produce two changes that conflict on the way back, so the workspace layer holds path-level leases: a task declares the files it expects to touch, and the scheduler will not start a second task that wants a path already leased.

Deleting a task keeps the commits on its branch. Nothing an agent does reaches your working copy.

Verification: the gate

This is what makes the difference between a farm and four terminal windows. No agent's own report can move a task to Done without passing through here.

  • Commands are yours — the repository's own checks, configured on the farm, run in the task's worktree.
  • A task's own list is added to the farm's, because the common case is “the usual checks, plus this one”. A task can also replace them entirely, for a subdirectory with its own toolchain.
  • Commands run in order and stop at the first failure. The cheap ones come first by convention, and running a twenty-minute suite after the type check already failed spends time to learn nothing. The ones that did not run show as pending, never as passed.
  • Output is drained continuously with bounded retention, so a noisy check cannot exhaust memory. Stopping a check or reaching its deadline terminates its whole process tree.
  • There is no shell in the path: a command is argv, not a string handed to sh.
  • Evidence is trusted only for a committed, clean task worktree — a passing run against uncommitted work proves nothing about what would merge.
Nothing configured is not a pass

A task that reaches review with nothing configured to check it says so, in those words. It does not read as verified.

Review: a second agent

One rule, and it is not negotiable: the agent that implemented a task may not be the one that approves it. A model asked to review its own work agrees with itself. The reviewer's decision is parsed out of its transcript into a structure, for the same reason a handoff is — a review that has to be read by a person before anything can happen is a review that has not automated anything.

The repository's own rules

Spagitty reads the repository's policy file and attaches it to every prompt. A farm without this produces agents that write in a house style nobody uses, add dependencies the project has refused, and reformat files as they pass. The fix is not a longer prompt; it is the repository saying what it wants, once, in a file that is committed and reviewed like everything else.

FileRole
AGENTS.mdAuthoritative. Wins wherever the files disagree.
CLAUDE.mdRead and appended under a heading naming its source.
.cursor/rulesSame.
.github/copilot-instructions.mdSame.

They are concatenated under headings that name where each came from, and the agent is told which one governs. They are not merged cleverly — a merge that silently dropped a rule would be worse than a prompt containing two. Sixty-four kilobytes is the cap: a rules file longer than that is a manual, and pasting a manual into every prompt is how a farm spends its budget on context rather than on work. If your repository has none, Spagitty will write you a starter one.

Scheduling

Tasks form a directed acyclic graph, and the scheduler runs whatever has no unfinished ancestors. That single rule is the whole of parallel execution. Up to eight agents work at once; a plan may hold twenty-four tasks; how many attempts a task gets before it needs a person is a setting rather than a constant.

The scheduler is a pure function — farm plus leases in, a list of decisions out. It starts nothing, spawns nothing and writes nothing, which is why the interesting behaviour is tested as a table rather than by running agents.

A queued task says why it is not running

Not “Pending”. The row carries the scheduler's own answer: which task is holding the same files, how many agents are working against the limit, that nothing installed can do this kind of work, or that the farm is not running. A task's own note — a verification failure, a reviewer's words — still comes first.

Watching it

The header is a ring

What is finished fills it, what is running is a brighter arc at its leading edge, and anything blocked colours the remainder — so an unfinished farm and a stuck one do not look the same at the same count. Above the plan, one chip per working agent names what it is on and for how long; the strip is absent when nothing runs.

The drawer has two tabs

Activity is what the farm did — tasks created, statuses moved, verifications run, merges landed — timestamped, filterable to one task, and as long as the history. Transcript is what one agent said, which is thousands of lines and belongs to one task at a time. Keeping them in one list would drown the record in the narration. The drawer drags to the height you want and collapses to its own tab bar.

Two controls, and they are not the same thing. Following is where the scrollbar is: the pane sticks to the newest line while you are at the bottom and lets go the moment you scroll up. Hold is a decision — it freezes the list so a line can be read while it is still arriving, and counts what arrived while it was held, so holding is never losing.

A quiet run says so, and is never stopped for you

After six minutes without a word, the chip and the row say how long it has been silent and the pulse stops. A model may think for a long time; killing it throws the work away, so the farm flags and leaves the decision where it belongs.

Nothing polls

A farm changes when an agent says something, which is at a model's pace and on no schedule. The backend emits, the store applies, and the screen is a function of the store. A snapshot is refetched shortly after a burst so nothing drifts if an event was missed.

It survives a crash

The farm is JSON under .spagitty/ inside the repository — excluded from git through .git/info/exclude, never committed, and deleted when the repository is.

FileHolds
farm.jsonThe farm and its tasks, rewritten after every state change and written by rename, so a crash mid-write leaves the previous state intact rather than a truncated file.
events.jsonlThe event log, one JSON object per line — a format a crash mid-append cannot corrupt, because the partial last line is simply dropped on read. Trimmed to two thousand entries on write.
agents.jsonThe per-repository agent registry: roles, enablement, argument overrides.
TranscriptsOn disk, per run, so the drawer can read a task's whole log back rather than holding it in memory.

On startup the service reconciles what is on disk against the worktrees that actually exist. JSON rather than SQLite is a deliberate choice with its reasoning written down — see persistence in the crate reference.

The starter page

A farm's first screen answers three questions in the order they are asked: what a farm is, how to start one, and whether this machine can run one. The goal field is on it, so starting a farm needs one sentence and no navigation. Three readiness rows say whether an agent was found, whether the repository has an AGENTS.md, and whether anything verifies the work — and none of them blocks starting, because a farm with no agent is still a plan.

Where the code is

The control plane is crates/spagitty-farm: model, adapters, workspaces, execution, verification, review, orchestrator, persistence. It calls spagitty-core for every git operation rather than reimplementing one, and it holds no Tauri types. Module by module: spagitty-farm. The screen is 1Q, and the commands that reach the crate are on the IPC reference.
