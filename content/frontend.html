How it is built

The frontend

SvelteKit 2 in SPA mode — ssr = false, prerender = false. Tauri serves a static bundle from disk; there is no server. Svelte 5 runes throughout, TypeScript, built and tested with Bun.

The rules

Five, and they shape everything else

src/lib/api.ts is the only module that calls invoke. A command rename is a one-file change.
One directory per screen, each with a store.svelte.ts and its components.
Stores export a single object with getters, never the $state variables themselves, so a screen cannot write another screen's state by accident.
Structural numbers come from metrics.ts. There is no height: 26px in any component.
Standard git terminology only. fetch, push, stage, hunk, stash@{n}, pick/squash/reword/drop, ours/theirs. No invented vocabulary, no friendly renaming of git concepts.

Shared modules

  • api.tsTyped wrappers around every Tauri command. Everything else talks in the types from types.ts.
  • types.tsThe wire types, mirroring the serde shapes in the Rust crates by hand. Kept in step deliberately rather than generated — the wire shape is small, and a generator would be more machinery than the problem needs.
  • metrics.tsStructural numbers, the single source of truth, published as CSS custom properties by applyMetrics. Carries ROW_PITCH, which Rust reads back at boot and compares.
  • nav.tsThe rail: screen codes, order, labels, and which count each row shows. The active item and the route are the same fact.
  • repo.svelte.tsThe open repository — which one, what HEAD is, and the rail counts. One is open at a time; opening another replaces it, which on the Rust side tears down the previous walk and watcher.
  • workspace.svelte.tsRepository tabs, including tabs onto linked worktrees.
  • session.tsWhat a launch resumes, as a sequence a test can watch.
  • themes.ts · theme.svelte.tsSixteen palettes as data, and which one is applied. Switching writes custom properties — no component re-render, no stylesheet swap.
  • scale.svelte.tsText size (90–130%) and interface zoom (100–200%), two independent dials that compose.
  • panels.svelte.tsThe panel registry: each panel names its CSS variable, its anchored edge and its range. Splitter takes any key.
  • format.ts · version.tsRelative times, and the build's own version.

The persistent frame

src/lib/chrome/ holds the title bar, toolbar, nav rail, repository tabs, status strip and resize edges. The window is created with decorations: false, so the platform draws no title bar and Spagitty draws its own — which is also why the title bar is the drag handle and the resize edges are a component.

Three things are mounted once, by the shell

Dialog (every confirmation), Notice (every result) and the command log drawer. An operation started on the graph can finish after the user has navigated away, and a dialog owned by a screen would take the question with it.

The shared UI kit

  • ui/Menu.svelteEvery right-click menu in the application is this component with a different list.
  • ui/DialogHost · dialog.svelte.tsEvery confirmation.
  • ui/NoticeToast · notice.svelte.tsEvery result.
  • ui/Splitter.svelteEvery resize handle. It measures the panel beside it rather than the window — the window's edge is the right reference only for the rail.
  • ui/columns.svelte.tsA table's columns: which are shown, in what order, how wide — per repository. Extracted from the graph when the Branches screen needed the same thing.
  • ui/liquidGlass.ts · liquidGlassMaps.tsThe refraction. The arithmetic is pure and tested without a window; the measuring half does nothing at all when there is no lens to filter — which is every component test.
  • ui/Icon.svelte · icons.tsThe icon set as data.
  • ui/BrandMark · RefChip · Chip · BtnThe small shared pieces.
  • ui/ScreenStub.svelteRendered by no route any more. It stays because it is how the next unbuilt screen says what it will be rather than pretending to be it — a half-built screen that looks real is harder to read than an honest empty one.

The command palette

src/lib/palette/ is a registry, not a list. commands.ts contributes the shell's own commands — navigation, the graph's view controls, appearance, and the two repository-wide git verbs — and a feature contributes its own next to itself, so no single file has to import every feature in order to name it.

It is the one place that picks its key notation from the platform at runtime, because macOS is a build target and printing Ctrl+ on a machine with no such key would be wrong.

Notable stores

The graph store

Rows live in a plain array, not in $state. A repository with 200,000 commits would mean 200,000 deeply-proxied objects, and every batch would pay to re-wrap them. Instead the array is untracked and a version counter is the reactive signal: appending a batch is O(batch), and consumers re-read what they need. Nothing in the store holds a DOM node — the row list is virtualised and the lanes are drawn on canvas.

Around it:

  • graph/lanes.tsLane drawing. One canvas covers the lane column for the visible window only.
  • graph/portrait.tsThe author portrait as a description, rendered two ways — canvas for the node, CSS gradients for the Author column — so a person has one face on screen.
  • graph/visibility.svelte.tsHide, solo, smart visibility, pin-to-left. Each resolves to a root set for a fresh walk.
  • graph/selection.svelte.tsA second selection, deliberately: the detail panel shows exactly one row, and the operations that act on several need their own.
  • graph/overlay.svelte.tsThe two things on the graph that are not commits — the work-in-progress node and the stashes.
  • graph/actions.tsWhat the menus actually do. Kept apart from the menus that describe them, because the sentence shown before a reset --hard is as much of the feature as the reset.

The farm store

Driven by events rather than a poll: a farm changes when an agent says something, which is at a model's pace and on no schedule. The backend emits, the store applies, and the screen is a function of the store. A snapshot is refetched shortly after a burst, so nothing drifts if an event was missed. It has an API module of its own, for the same reason the shared one exists.

The delight layer

src/lib/delight/ is deliberately a sink: git actions push events into it and it pushes nothing back. It holds no reference to repo — the shell tells it which repository and which identity it belongs to — because almost everything that reports a git operation is reachable from repo, and importing it back would close a cycle through half the frontend.

engine.ts is pure, so the rule set is tested as a table rather than by driving the application, and nothing in the directory can fail a git operation: every call site is discarded and recording swallows its own failure. Its record lives in localStorage, keyed by repository path, beside the theme and the column layouts — a lost record is a record of badges, not of work, and git remains the only authority on what actually happened.

The launch sequence

session.ts holds what a launch resumes, as a sequence a test can watch: read the launch path and open it, or else reopen the tab the last session was on, then land on its route. It used to live inside the shell's onMount, where none of that could be asserted.

Testing the frontend

Components are mounted for real against happy-dom, through vitest. The helpers live in src/testing/: mount.ts renders a component and returns query handles, and there are reactive stand-ins for the two stores the chrome reads.

Why the stand-ins hold $state

A stub built from ordinary properties renders once and never updates, so every test about a change would pass by rendering the initial value. The stand-ins hold real reactive state for exactly that reason.

The coverage floor is branch coverage — 65% over src/lib/**. src/testing/** is excluded because it is scaffolding, and src/routes/** because those files are the screens' shells and their logic lives in src/lib. Details on testing.

Development vs production styles

Development injects scoped styles with component JavaScript (emitCss: false); production continues extracting CSS assets. That is not a preference — it avoids a case where a stylesheet request arriving before its component made the plugin's cold-cache fallback serve Svelte source as CSS. A headless test checks the installed pipeline against that request order, because build success alone does not test it.
