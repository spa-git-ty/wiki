What Spagitty is

A local-first desktop Git client for repositories where people and coding agents commit side by side, and the gateway to a Git-managed agent farm. It runs on Linux, macOS and Windows, it is free software under the GPL, and it has no account, no server and no model of its own.

The problem

Work arrives faster than it can be read. A repository where several people and several coding agents are all committing produces history at a rate that outstrips anybody's ability to follow it in a terminal, and the tools most of us reach for were designed for a slower shape of work — one author, one branch at a time, a review that happens once at the end.

What breaks first is not the writing. It is the reading: what happened, who did it, whether it was checked, and what to do next. A repository without a readable history is a plate of tangled pasta. Spagitty straightens the strands.

Where the name comes from

Spagitty — spa-gi-ty — is spaghetti plus Git. It is also the mark: four dark strands that begin tangled at the top of an amber plate and resolve into straight, parallel paths below. The metaphor is kept literal on purpose. Tangled and straightened, pasta and strands. We do not extend it into chefs and kitchens in product copy; that register belongs to the delight layer, where it is deliberately a joke.

What it does

Two things, and the second is built on the first.

It reads, reviews and lands the work

Spagitty is a full desktop Git client: a lane graph of history with hide, solo, pin and smart visibility; a working copy that stages by file, hunk or line; diffs with syntax highlighting, image comparison and binary size deltas; file history with rename following and a blame gutter; branches, tags, stashes, the reflog, worktrees and submodules as first-class screens; interactive rebase with a preview before anything runs; in-app conflict resolution or your own merge tool; and pull requests read, reviewed, created and merged against GitHub, GitLab and Bitbucket Cloud.

See the feature reference for the whole list.

It runs the agents

Set a goal. Spagitty cuts it into tasks and hands them to the coding agents already installed on your machine, up to eight at a time, each on its own branch in its own worktree. Verification runs your repository's own commands in the task's worktree. Review is performed by a different agent than the one that wrote the change. You choose where you stand, from Manual — nothing runs by itself — to Unattended.

The whole feature is written up on the agent farm.

The principles

Local-first, and checkably so

Repositories stay on disk. There is no account step, no cloud to log into, and no server of ours in any path. The only network boundary in the whole workspace is one file — crates/spagitty-core/src/forge/http.rs — talking to the forges you connected, when you ask it to. A test asserts that exactly one HTTP client exists, that it is declared only in that crate, and that the webview links none at all.

Nothing here is a model

Spagitty ships no model and no API key. The agents it runs are programs already on your machine, invoked as you, with your credentials. We never describe Spagitty as “AI-powered”, because that trades away the one thing a local-first tool has: you can tell what it is doing.

An agent's own report is not evidence

The farm's status machine has no edge from “the agent said it finished” to Done. Verification runs the repository's own commands; review is performed by a second agent; and every handoff goes through Spagitty rather than between agents, so there is one audit trail and one place that decides what happens next.

Say what a thing does, including when it does nothing

A toggle that is not honoured yet names the item that will honour it. A screen that cannot do something says so where you would look for it, rather than failing silently when clicked. “May conflict” on the rebase preview uses the word may, because knowing for certain would mean performing the merges — and claiming a clean result we cannot prove would be the worse lie.

Git is the authority, not our preferences

Whether a commit will be signed is read from commit.gpgsign and its neighbours, not from a Spagitty setting pretending to be that. Branch names are validated by git, because a second implementation of check-ref-format could only disagree with it. Clearing an identity field runs git config --unset rather than writing an empty string, because a configured empty email is a different thing from an unset one.

The destructive thing is the one that asks

Staging, unstaging and committing only move work forward, so they do not interrupt. Discard, delete, reset --hard, force push and rebase do, and the confirmation says what actually goes away — including, where it applies, the exact command that brings it back.

What Spagitty is not

Not thisWhy
A hosted forgeGitHub, GitLab and Bitbucket stay outside. Spagitty reads and writes to them through a token you issue.
A CI systemVerification runs your repository's commands locally, in a task's worktree. It is a gate, not a pipeline.
A model, or a wrapper around oneNo inference happens in Spagitty. The agents are separate programs you installed.
A productivity leaderboardThe badge screen ranks agents by first-pass rate in this repository, never by volume, and never puts a human on the same table.
A telemetry surfaceNothing is counted, sampled or sent. There is nowhere for it to go.

Who it is for

  • People who review more than they write. The graph is the primary navigation surface rather than a read-only report — almost every operation is one right-click away from a commit or a branch label.
  • People supervising coding agents. The farm is a supervision screen: a plan on the left, the selected task in the middle, and what just happened along the bottom, so supervising does not mean navigating.
  • People learning how a desktop Git application is put together. The architecture is three layers with hard seams, and the working record keeps the reasoning — including the defects found along the way — rather than only the result.

LayerBuilt with
Window & shellTauri 2 — WebKitGTK on Linux, WKWebView on macOS, WebView2 on Windows
