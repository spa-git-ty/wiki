Using Spagitty

Privacy & security

Spagitty has no telemetry, no analytics, no account of ours and no server of ours in any path. Repositories stay on disk. This page says exactly what that means, and — more usefully — how the claims are made checkable rather than promised.

What Spagitty does not do

  • No telemetry. Nothing is counted, sampled, batched or sent. There is nowhere for it to go.
  • No analytics, crash reporting or usage metrics. Same reason.
  • No account. There is no Spagitty sign-in, because there is no Spagitty service.
  • No model, no key. Nothing in Spagitty performs inference, and nothing ships a credential for a provider.
  • No repository upload. Repositories are read where they sit. Nothing copies, syncs or indexes them anywhere.
  • No password prompt of our own. Credentials go through git's own helpers, which is where OS keychain integration already lives.

What does cross the network, and when

WhatTo whereWhen
Pull request data The forge you connected — GitHub, GitLab or Bitbucket Cloud When the Pull requests screen refreshes, carrying a token you issued, asking for pull requests you can already see in a browser. No repository contents, no paths, no commit messages.

That is the complete list.

Two boundaries that make it checkable

A promise about what an application sends is only as good as the number of places that could send something. Spagitty keeps both counts at one.

One HTTP client, in one file

The original promise was that no HTTP client was linked in either language, with a test to keep it that way. Reading pull requests could not survive that, so it became a narrower promise that is still worth having and is still tested: exactly one client, ureq, declared only in spagitty-core, and reachable from exactly one file — crates/spagitty-core/src/forge/http.rs.

The webview links no HTTP client, makes no request, and never holds a token. Its content security policy allows self, data URIs and Tauri's own asset protocol, and nothing else — so even a rendered pull request description cannot reach out.

One process spawner, in one file

crates/spagitty-core/src/shell.rs is the only module in the workspace that spawns a process. That is a correctness rule first — see the git binary boundary — but it is also what makes “what did this application actually run” answerable at all.

Why a personal access token rather than OAuth

A token is issued, scoped and revoked by you without touching anything else you own. OAuth would need a redirect listener and a client secret shipped inside a GPL binary anybody can read — which is not a secret. The login is read back from the host rather than typed, so the account shown is the account the token actually belongs to.

Credentials are removed on the way in

A clone URL can carry a token — https://user:token@host/repo.git — so the command record strips the userinfo before the entry is stored. An entry that never held the secret cannot leak it through the copy button, or through a later reader who assumed display was doing the work.

The agent farm

  • Agents run as you. Same user, same environment, same credentials. Spagitty adds no key and no model.
  • Each task is isolated to its own worktree. Nothing an agent does reaches your working copy, and path-level leases stop two agents editing the same file.
  • The farm's state stays in the repository — .spagitty/, added to .git/info/exclude, never committed, deleted with the repository.
  • Verification runs argv, not a shell string. There is no shell in the verification path, so a command cannot be turned into three by a stray character.
  • Stopping means stopping. Cancelling a run or reaching a deadline terminates the whole process tree — a process group on Unix, a job object on Windows, assigned before the child can spawn anything of its own.
What Spagitty cannot promise for you

A coding agent you run is a program with your permissions, talking to whatever service it was built for. Spagitty isolates its working tree and records what it did; it does not, and cannot, sandbox what that agent sends to its own provider. Choose the agents you install, and use the autonomy dial that matches how much you trust them.

Supply chain

Every dependency's licence is identified and permitted, checked on every change. Known-vulnerable dependencies fail the build at the high level or above, and an advisory that cannot be fixed is recorded by id, with its crate and its reason, so anything not listed still fails — the line between recording a risk and switching the check off. Secret scanning runs over every change. The whole contract is on CI/CD & releases.

Reporting something

Spagitty is free software and the source is the specification: if you believe something here is wrong, the file that would prove it is named on this page. Open an issue on the repository. For a suspected vulnerability, say what the class of problem is rather than posting a working exploit.
