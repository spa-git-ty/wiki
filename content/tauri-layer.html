How it is built

The Tauri layer

src-tauri owns the window, the command surface and the background workers. It is deliberately thin: it holds the open session — one repository at a time — and forwards to the core. No git logic lives here.

The files

  • lib.rsCommand registration, and the run sequence. Owns the window and the workers; all git logic is spagitty-core's.
  • commands.rsOne #[tauri::command] per operation. Holds the open session, forwards to the core, and converts errors to strings for the webview.
  • farm.rsThe farm's Tauri layer — thin in the same way. Holds the open farm, forwards to spagitty-farm, and turns each FarmEvent into one webview event. State of its own, with a different lifetime from the graph session.
  • graph_worker.rsOne thread per open repository, walking history and streaming rows.
  • search_worker.rsOne thread per query. Starting one cancels the one before.
  • clone_worker.rsOne thread per clone, owning the git process — so cancelling is a signal rather than a request.
  • network_worker.rsFetch and push, watched while they run. Both were fire-and-wait: --progress was passed to git and nothing read it.
  • rebase_worker.rsOne thread watching git rewrite history, so the session lock is never held while it runs.
  • watch.rsFilesystem watching over the git directory. Spagitty does not poll — notify tells the UI when something it displays has actually changed.
  • command_log.rsThe adapter between record.rs and the window: one observer registered at startup, forwarding each entry as an event.
  • recents.rsThe repositories the user has opened. Application state, not repository state — a record of what the user did.
  • settings.rsSpagitty's own preferences, beside the repository list. None of it is a fact about a repository.
  • accounts.rsWhich hosting accounts are connected — a host and a login. The token is in the keychain.
  • profiles.rsNamed identity profiles, and applying one locally or globally.
  • about.rsBuild identity and the dependency licence list — both halves of the GPL-3 obligation the About section exists to meet.
  • platform.rsHost facts that must be true before the webview builds its first frame. Nothing here is git or Spagitty.
  • testing.rsScaffolding for this crate's own tests.

Why the workers are threads

Each long-running job owns a thread and its own cancellation, and each one is a slightly different shape for a reason its header explains:

WorkerWhat is different about it
GraphOne per open repository, long-lived. It walks lazily — the worker does nothing until the store asks for rows.
SearchOne per query, not per repository. Starting one cancels the one before, and rows carrying a stale token are dropped rather than rendered — which is what makes searching on a keystroke safe.
CloneOwns a child process rather than a walk, so cancellation is a signal. Removal of a partial clone happens after the child is reaped, never after the kill signal, or the two race and files reappear behind it.
NetworkExists so a fetch says something while it runs. It reads git's progress rather than waiting for the exit code.
RebaseRuns without holding the session lock, with progress read from git's own state counters.

Tokens, not cancellation races

Both streaming workers stamp every batch with the token of the walk that produced it. A superseded walk is discarded by ignoring its rows rather than by successfully cancelling it in time — which is a race the frontend cannot win and does not have to.

The farm's commands are async

Its commands are #[tauri::command(async)] rather than plain, because they take locks that agent threads hold — and a blocking command runs on the thread that paints the window. A farm that planned for thirty seconds froze the window for thirty seconds.

Platform facts

platform.rs arranges the webview's environment as the first statement of run — before the builder, and while the process is still single-threaded, which is the only state in which setting an environment variable is sound.

It sets WEBKIT_FORCE_COMPOSITING_MODE=1, which keeps the whole page on the GPU rather than letting WebKitGTK fall back to software for the parts its heuristics misjudge.

It deliberately does not set WEBKIT_DISABLE_DMABUF_RENDERER, and that is a recorded reversal. It used to be set to 1 on every Linux start, because WebKitGTK's DMABuf renderer cannot allocate a GBM buffer on some driver and compositor combinations, and a webview with no frame to present is a white window for the whole session. The cost of that workaround was written down and then lived with for too long: with the renderer off, every Linux host repaints through shared memory, on the CPU — including the hosts that never had the bug. On a real window that is a frame that lags the pointer during a resize and a history that scrolls at a fraction of the display's rate.

The accelerated path is the default now. A host that hits the GBM bug sets the variable in its own environment, which the process still honours — along with an explicit value for either variable in either direction.

The command surface

Around 130 commands, grouped by what they are for. The full list, with what each one does, is on the IPC reference.

GroupShape

One special command

graph_visibility is worth naming: hide, solo, smart visibility and pin-to-left all resolve to a root set for a fresh walk rather than to a filter over rows the frontend already has. Filtering client-side would leave the lanes drawing edges between commits that are no longer parent and child.

Events

EventCarries
graph-rowsA batch of commit rows, stamped with its walk's token.
graph-doneThe walk finished.
search-rows / search-doneThe same shape, per query.
clone-progress / clone-doneGit's own parsed progress, and the outcome.
network-progress / network-doneFetch and push while they run.
rebase-progress / rebase-doneRead from git's state counters, not parsed from output.
repo-changedThe watcher saw something. Refs moving debounces into a re-read and a re-walk; a worktree change re-reads the counts only.
git-commandOne execution, as shell.rs recorded it.
farm-eventOne FarmEvent, internally tagged — one channel rather than sixteen, because the screen keeps one activity list and one ordering.

Testing a layer that owns a window

Two things make it possible to test this crate against real repositories, headlessly.

  • Everything is generic over R: tauri::Runtime, so tauri::test::mock_app can supply an AppHandle<MockRuntime> where the real one supplies a Wry handle.
  • spagitty-core's fixtures are public behind a feature, which src-tauri enables as a dev-dependency — one fixture builder for the workspace rather than two things building repositories with the git binary. Nothing enables the feature outside tests, so a release build carries neither the fixtures nor tempfile.

testing.rs holds what an event test needs beyond that: a mock application managing the real state, an Emitted<T> collector with at_least(n) and no_more_than(n), and finishes_promptly, which puts a deadline on a drop — dropping a worker joins its thread, so a worker that ignored its shutdown would hang the test runner rather than fail it.

It also points HOME and the platform's other configuration variables at a temporary directory, once for the whole test binary: open_repo writes to the recent-repositories list, and a test run must not add rows to the list of repositories you have opened.

The window

Created undecorated and transparent at 1280×800, with a content security policy that allows self, data URIs and Tauri's asset protocol and nothing else. Everything a person reads as “the window” is drawn by the application — see the window itself and the glass.
