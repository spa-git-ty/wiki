How we work

Testing

What is checked, how, and what is deliberately not. Anything that reads a repository is tested against a real one; anything pure is tested as a table; and the parts that need a window say so rather than pretending a mock proved something.

Headless

cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace

bun run check          # svelte-kit sync && svelte-check
bun run test           # vitest, run through bun
bun run coverage       # vitest with the coverage floor enforced

Coverage of first-party code is measured on both sides and both must clear their floor:

cargo llvm-cov --workspace \
  --ignore-filename-regex '(fixture|testing)\.rs' --summary-only
bun run coverage
SideFloorScope
Rust70% linesThe workspace, with fixture.rs excluded — it is test scaffolding, and counting a helper every test exercises would lift the figure without any product code being tested.
Frontend65% branchessrc/lib/**. src/testing/** is excluded for the same reason, and src/routes/** because those files are the screens' shells and their logic lives in src/lib.

They are not the same number, and neither is a line count for the whole tree. Each floor is defined once — in the workflow for Rust, in vite.config.ts for the frontend — so bun run coverage fails locally for exactly the reason it would fail in CI.

Fixtures in the Rust tests

crates/spagitty-core/src/fixture.rs builds real repositories with the git binary — not with gix, because a fixture built by the library under test would agree with it by construction.

FixtureIs
Fixture::empty()An initialised repository with no commits.
Fixture::woven()The standard history — a merge, a merged branch and an unmerged one, tags of both kinds, stashes — with a clean working copy.
Fixture::dirty()The same, with work in progress.

Each lives in a temporary directory that is removed with it.

Fixtures in the Tauri layer

src-tauri tests the graph worker, the watcher's debounce and the session against a real repository too. Two things make that possible:

  • Everything in src-tauri that touches the application is generic over R: tauri::Runtime, so tauri::test::mock_app can supply an AppHandle<MockRuntime>.
  • spagitty-core's fixtures are public behind a fixture feature, which src-tauri enables as a dev-dependency — one fixture builder for the workspace rather than two things building repositories with the git binary. Nothing enables it outside tests, so a release build carries neither the fixtures nor tempfile.

src-tauri/src/testing.rs holds what an event test needs beyond that: a mock application managing the real state, an Emitted<T> collector with at_least(n) and no_more_than(n), and finishes_promptly, which puts a deadline on a drop. That last one matters — dropping a worker joins its thread, so a worker that ignored its shutdown would hang the runner rather than fail.

It also points HOME and the platform's other configuration variables at a temporary directory, once for the whole test binary: open_repo writes to the recent-repositories list, and a test run must not add rows to the list of repositories you have opened.

The one test that crosses the language boundary

ROW_PITCH exists twice: in src/lib/metrics.ts, which is the source of truth, and in crates/spagitty-core/src/graph.rs, which describes lane elbows in row units and so needs the same number.

Two copies of a constant in two languages drift — and they did. The geometry moved on one side while doc comments on both sides claimed a test was holding them together. There was no such test.

graph::tests::row_pitch_matches_the_frontend is that test now. It resolves the TypeScript file from CARGO_MANIFEST_DIR, reads the export const ROW_PITCH declaration out of it, and asserts it against the crate's constant — failing with both values named so the message says which side moved.

It is the only test that reads another language's source, and it earns that by being about the only constant duplicated across the boundary. Anything else needing to cross should go through the existing IPC types.

The frontend

Components are mounted for real against happy-dom. The helpers live in src/testing/: mount.ts renders a component and returns query handles, and there are reactive stand-ins for the two stores the chrome reads.

The stand-ins hold real state

A stub built from ordinary properties renders once and never updates, so every test about a change would pass by rendering the initial value.

What is tested away from the markup

Wherever the interesting decision is a pure function, it lives beside the component and is tested as a table: the lane fold, the split-view pairing, the syntax tokeniser, the achievement engine, the farm's scheduler and router, the settings screen's sentences about where a value came from, the divergence bar's geometry, and the glass maps' arithmetic.

Tests that hold a rule rather than a behaviour

TestFails if
ThemesAny of the sixteen palettes drops below 4.5:1 for ordinary text or 3:1 for secondary text, the accent or a lane colour — computed with translucent tokens composited over what shows through them. Or if two families ever share an accent hue.
Settings sectionsA chip is added without an explicit branch behind it. The screen used to have an {:else} catch-all, and one chip silently drew the wrong section for weeks.
Pull requestsA host's name appears anywhere in the screen, or more than one HTTP client exists, or one is declared outside spagitty-core, or it is reachable from more than one file.
ConflictsReading a conflicted repository modifies the index or leaves a lock behind.
All repositoriesReading a repository card modifies that repository's index.
Interactive rebaseThe generated todo list disagrees with git rev-list --reverse --no-merges.
The working recordThe index under agile/ and the tree disagree — a missing row, a row with no document, a status that does not match the item, or a cited identifier that resolves to nothing.
Brand driftThe generated icons or brand collateral differ from what is committed.
Development stylesA stylesheet request arriving before its component makes the Svelte plugin's cold-cache fallback serve source as CSS. Build success alone does not test that request order.

The farm's own tests

crates/spagitty-farm/tests/pipeline.rs takes a task end to end against a real repository, with a shell script standing in for the agent — which is the point. An integration test that needed a model installed would run nowhere, and one that stubbed the process boundary would not exercise the boundary. Everything else in the crate is pure and tested as a table: the scheduler, the router, the dependency graph, the verifier's command composition, the reviewer's second-agent rule, and the branch-name derivation.

The fixture repository for manual sweeps

The manual sweeps assume a repository with a merge, a branch that is merged and one that is not, tags of both kinds, stash entries, a binary file, a dotfile, a deeply nested path, and a dirty working copy with both staged and unstaged changes. Build it in a scratch directory — never inside the repository: 

FIX=/tmp/spagitty-fixture
mkdir -p "$FIX" && cd "$FIX"
git init -q -b main
git config user.name "Ada Lovelace"
git config user.email ada@example.com
git config commit.gpgsign false

seq 1 40 | sed 's/^/line /' > core.txt
printf 'alpha\nbeta\ngamma\n' > notes.md
printf '# fixture\n' > README.md
mkdir -p src/deep/nested
printf 'fn main() {}\n' > src/deep/nested/main.rs
printf '\x00\x01\x02binary\x00data\n' > logo.bin
printf '.cache/\n' > .gitignore
git add -A && git commit -q -m "Initial import"

for i in 1 2 3 4 5; do
  printf 'entry %s\n' "$i" >> notes.md
  git commit -q -am "Add note $i"
done

git switch -q -c feature/split-view
sed -i 's/^line 3$/LINE THREE/' core.txt
git commit -q -am "Rewrite line 3 in core"
printf 'split view work\n' > split.txt
git add split.txt && git commit -q -m "Start the split view"

git switch -q main
sed -i 's/^line 38$/LINE THIRTY-EIGHT/' core.txt
git commit -q -am "Rewrite line 38 in core"
git merge -q --no-ff feature/split-view -m "Merge feature/split-view"

git switch -q -c chore/tooling main
printf 'tooling\n' > tools.txt
git add tools.txt && git commit -q -m "Add a tooling note"

git switch -q main
git branch merged/already-in-main main~1
git tag -a v0.1.0 -m "First tag" main~2      # annotated
git tag v0.2.0                                # lightweight

printf 'work in progress\n' >> notes.md
git stash push -q -u -m "wip on notes"
printf 'second stash\n' >> README.md
git stash push -q -m "wip on readme"

printf 'uncommitted change\n' >> core.txt
printf 'brand new file\n' > untracked.txt
printf 'staged change\n' >> notes.md
git add notes.md

That leaves 11 commits, 4 local branches, 2 tags, 2 stash entries, one staged file, one unstaged file and one untracked file.

A conflicted fixture

The Conflicts screen needs a repository stopped mid-merge, which is a state the other screens should not be tested against. Build it separately: 

CFL=/tmp/spagitty-conflict
mkdir -p "$CFL" && cd "$CFL"
git init -q -b main
git config user.name "Ada Lovelace"
git config user.email ada@example.com
printf 'one\ntwo\nthree\n' > shared.txt
git add -A && git commit -q -m "Base"

git switch -q -c theirs
printf 'one\nTHEIRS\nthree\n' > shared.txt
git commit -q -am "Their change"

git switch -q main
printf 'one\nOURS\nthree\n' > shared.txt
git commit -q -am "Our change"

git merge theirs || true    # stops with a conflict, which is the point

The visual sweep

The application is driven for real, not screenshotted from a mock.

bun run tauri dev -- -- -- /tmp/spagitty-fixture

Driving it without a desk

A human tester works the window directly. An automated sweep on a Wayland session cannot, for two reasons that both look like application bugs and are not:

  • The pointer cannot be moved. XWayland refuses XWarpPointer, so xdotool mousemove silently does nothing and every click lands wherever the real pointer happens to be.
  • An unfocused window never repaints. The compositor only paints what it shows, so a capture returns whatever was in the backing store — usually the first frame, before the stylesheet's custom properties were applied. It looks like a broken layout and is a stale image of a correct one.

A plain X server has neither problem, and is also the polite option — nothing steals focus:

Xvfb :99 -screen 0 1600x1000x24 -nolisten tcp &

env -u WAYLAND_DISPLAY DISPLAY=:99 GDK_BACKEND=x11 \
bun run tauri dev -- -- -- /tmp/spagitty-fixture

-u WAYLAND_DISPLAY is the part that is easy to miss: with it set, GTK prefers the Wayland backend and connects to the real session regardless of DISPLAY, and the window opens on the desktop instead of the virtual screen.

Findings go into that item's sweep document under agile/testing/ as filled-in results — not into a commit message.

What is deliberately not tested

  • Drag gestures, on their own. Every reorder that can be dragged can also be done from the keyboard, and the store owns the ordering — so the behaviour is tested through the keyboard path and the component only reports intent.
  • The glass, visually. The arithmetic is pure and tested; the rendering is a WebKit behaviour, and the measuring half deliberately does nothing when there is no lens — which is every component test.
  • Whether a rebase will conflict. Knowing for certain means performing the merges, which is execution. The screen says “may conflict”, in that word.
