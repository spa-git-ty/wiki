How it is built

spagitty-farm

The agent farm's control plane: a goal, the tasks it was cut into, and the agents working them. It orchestrates and nothing else — every git operation it performs is spagitty-core's, and it holds no Tauri types either.

What the farm does, from the outside, is on the agent farm. This page is the crate.

Three rules the crate is built around

An agent saying “done” is not done. There is no transition from an agent's own report to Done; verification and a review by a different agent are in the path and cannot be skipped.
Agents never talk to each other. Every handoff goes through the service, so there is one audit trail and one place that decides what happens next.
Nothing an agent does reaches the user's checkout. Every task runs in its own worktree on its own branch.

model/ — the vocabulary#

Everything here is data. No process is spawned, no file is written and no git command runs from this module tree — deliberately, because these types are what everything else agrees on.

  • model/farm.rs Farm, FarmStatus, Autonomy (Manual, Assisted, Semi-automatic, Automatic, Unattended) and Permissions. A farm belongs to a repository, and there is one open at a time.
  • model/goal.rs One sentence from the user plus the constraints they want honoured. Separate from Farm because a goal outlives a run.
  • model/task.rs Task, TaskStatus (11 states), TaskKind (9 kinds), TaskPriority and TaskOrigin — the last being what lets the screen show who asked for a task. A task is machine-readable on purpose: “never rely entirely on free-form prose” is what makes the difference between a farm and a chat window.
  • model/agent.rs AgentDefinition, AgentProvider, AgentCapability, AgentRole, AgentInputMode, AgentAvailability. An agent must not be represented only by the path to its executable — the reason shows up the first time two of them are the same binary with different arguments.
  • model/run.rs One execution of one agent against one task. A task can be run more than once — a review asking for changes, a verification failure, a retry after a crash — so the run is the record, not the task.
  • model/handoff.rs What an agent hands back, in a fenced structure every agent returns: status, a test report, proposed tasks. Both halves matter — the structure, so Spagitty can act, and the prose, so a person can read what happened.
  • model/event.rs FarmEvent — one internally-tagged enum rather than a Tauri event per kind, because the screen keeps one activity list and one ordering. Sixteen variants, from TaskCreated through VerificationFinished and ReviewCompleted to MergeCompleted. Recorded wraps one with the time it happened, which is what makes a log a log.

agent/ — the providers#

Nothing above this module knows the name of a provider's executable or the shape of its command line. Each adapter knows exactly one thing: how to invoke its own CLI without a terminal.

  • agent/adapter.rsThe one interface every provider implements — AgentAdapter, AgentRunRequest, AgentCommand. Synchronous, with the reasoning in its header.
  • adapters/claude.rsClaude Code, in print mode: claude -p <prompt> runs the whole turn to completion with no terminal attached and writes the transcript to standard output.
  • adapters/codex.rsCodex. codex exec <prompt> is the non-interactive subcommand; bare codex would open a session.
  • adapters/cursor.rsCursor. The command is cursor-agent, not cursor — that is the editor, and running it here would open a window.
  • adapters/pi.rsOh My Pi, which takes its prompt on standard input.
  • adapters/custom.rsAn agent Spagitty has never heard of. A list of future providers is a list of releases if each one needs an adapter, so a configured command with a prompt token is a settings change instead.
  • agent/detector.rsFinding what is installed. Walks PATH itself rather than shelling out — with the reasoning in its header.
  • agent/registry.rsThe join between two things that must not be confused: what this machine has, and what the user has said about it.

workspace/ — where the work happens#

  • workspace/branch.rs Naming the branch and the directory a task works in — spagitty-farm/<task>/<provider>. Both names are derived, never chosen, and derived here, because the branch name is how the graph, the worktree list and the Farm screen find each other. task_of and provider_of read it back; a glob over NAMESPACE cleans up a farm without touching anything the user named.
  • workspace/worktree.rs A working tree of its own for every task. Two agents in one checkout is not a race that shows up occasionally — it is one agent reading another's half-written file. FARM_DIR is .spagitty, added to .git/info/exclude so a farm is never committed.
  • workspace/lock.rs Path-level leases. Worktrees stop two agents corrupting each other's files; leases stop two of them editing the same path and producing changes that conflict on the way back. EVERYTHING is the lease a task takes when it cannot say what it will touch.
  • workspace/cleanup.rs Told what is left over rather than which task to clean — a different question from removing one worktree, and the one that matters after a crash.

execution/ — running an agent#

  • execution/process.rsOne thread per run rather than an async runtime, with the reasoning in its header. Cancellation, Session, Ended.
  • execution/tree.rsA process tree owned by one run. Windows starts the child suspended so nothing can escape before job assignment; Unix assigns a process group at spawn. Stopping a run stops its descendants.
  • execution/log.rsThe transcript on disk rather than a String in memory — which is what lets the drawer read a task's whole log back after the fact, and what stops a long session growing.
  • execution/narrate.rsTurning what an agent prints into something a person can watch. Verbatim for providers that emit plain text, ClaudeStream for a structured one.

orchestrator/ — deciding what happens next#

The graph says what could run, the router says who would do it, and the scheduler puts the two together with the farm's own limits. All three are pure.

  • orchestrator/dependency.rs Tasks form a directed acyclic graph and whatever has no unfinished ancestors may run. That single rule is the whole of parallel execution. validate refuses a cycle.
  • orchestrator/router.rs Rule-based and deliberately not clever: a task kind maps to a preferred role, the registry finds an agent for that role, and if there is nobody the task goes to whoever can code. A scoring function weighing historical success against cost against context fit is untestable until there is history to test it with — and until then it is a random number generator with a good story. Scoreboard is the observable half of the eventual answer: it counts what actually happened per agent, which is a fact rather than an opinion. Nothing schedules on it yet.
  • orchestrator/scheduler.rs A pure function: farm plus leases in, a list of Decisions out. It starts nothing, spawns nothing and writes nothing — which is why the interesting behaviour is tested as a table. why_waiting is what a queued row shows instead of “Pending”.
  • orchestrator/planner.rs Turning a sentence into a plan, and a task into subtasks. MAX_TASKS and MAX_SUBTASKS bound what a planner may produce; adopt and adopt_under are how a proposed plan becomes real tasks once a person has said yes.

verification/ — the gate#

The module that makes the difference between a farm and four terminal windows: no agent's own report can move a task to Done without passing through here.

  • verification/verifier.rs commands_for composes the farm's list with the task's — added by default, because the common case is “the usual checks, plus this one”; replaced when the task says so, for a subdirectory with its own toolchain. run executes them in order and stops at the first failure: the cheap ones come first by convention, and running a twenty-minute suite after the type check already failed spends time to learn nothing. The ones that did not run show as pending, never as passed.
  • verification/command.rs One command, and how it is run. No shell — split turns a command into argv, so a stray character cannot turn one command into three. TIMEOUT and OUTPUT_BYTES bound how long a check may run and how much of its output is kept.
  • verification/evidence.rs Evidence is trusted only for a committed, clean task worktree. CheckedCommit and ReviewedCommit tie a pass and an approval to the commit they were actually about, so a later change cannot inherit them.

review/ — a second opinion#

  • review/reviewer.rs One rule, and it is enforced here: the agent that implemented a task may not be the one that approves it. A model asked to review its own work agrees with itself. check is the assertion; pick chooses the reviewer.
  • review/decision.rs Decision, Issue, Severity — parsed out of the reviewer's transcript in the same way a handoff is, and for the same reason: a review that has to be read by a person before anything can happen is a review that has not automated anything.

persistence/#

The farm on disk, so a crash is an interruption rather than a loss. JSON files rather than SQLite, and the reasoning is written down: SQLite is a C library, a licence to review, a build-time dependency on every platform Spagitty ships to, and a schema-migration story for a desktop application that currently has none — and the rest of Spagitty's own state is already JSON.

NeedHow it is met without a database
TransactionalEvery write goes to a temporary file and is renamed over the target. rename within a directory is atomic on every filesystem Spagitty supports, so a farm is never half-written.
Crash recoveryThe farm is written after every state change, so what is on disk is what was true at the last transition. The service reconciles it against the worktrees at startup.
HistoryEvents append one JSON object per line — a format a crash mid-append cannot corrupt, because the partial last line is dropped on read. Trimmed to MAX_EVENTS (2,000) on write.
QueryingNot a real need at this size. A farm has a dozen tasks and a few hundred events, and the query is “show me all of them”.

If a farm ever grows to the size where that hurts, the answer is a Store trait with a second implementation — and the shape here is already that trait's shape.

policy.rs and context.rs#

policy.rs reads the repository's own rules. AGENTS.md is authoritative; CLAUDE.md, .cursor/rules and .github/copilot-instructions.md are read anyway, because a repository that already wrote its rules down should not have to write them a third time to use a farm. They are concatenated under headings naming their source and the agent is told which one governs — not merged cleverly, because a merge that silently dropped a rule would be worse than a prompt containing two. MAX_BYTES is 64 KB: a longer rules file is a manual, and pasting a manual into every prompt is how a farm spends its budget on context rather than on work.

context.rs is what an agent is told — implementation, review, planning and decomposition each build their own, and the module exists to enforce the rule about what may go into one.

service.rs#

The API, and the only module that changes anything. Every other module in the crate is either data or a pure function over data; this one holds the state, spawns the processes, writes the files and moves tasks between statuses. Observer is how the Tauri layer receives events without the crate knowing what a window is.

Testing it#

tests/pipeline.rs takes a task end to end against a real repository, with a shell script standing in for the agent — which is the point: an integration test that needed a model installed would run nowhere, and a test that stubbed the process boundary would not exercise the boundary. The scheduler, the router, the dependency graph and the verifier are all pure, so their behaviour is tested as tables rather than by running agents.
