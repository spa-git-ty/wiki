Feature reference

Everything Spagitty ships, grouped by what you are trying to do. Each group links to the screen it lives on and, where the reasoning is interesting, to the page that explains it.

Reading history#

The commit graph#

  • Streamed and virtualised. Rows arrive in batches from a worker thread and never move once drawn, so a repository with a hundred thousand commits is readable immediately. The lane column is drawn on a canvas covering only the visible window — a repository with 200,000 commits draws the same number of paths as one with 40.
  • Lanes, branches and tags. Branch and tag chips sit in a gutter of their own, starting at the column's left edge so every row's first chip is at the same x. A branch chip carries its own divergence.
  • Author portraits, generated locally. A node is a portrait computed from the author's email — never fetched. A picture per author would be a request per author on the most performance-sensitive screen, would hand the committer list to whoever was asked, and would make an offline repository look different from an online one. A merge is a plain dot rather than a face: it is where two lines join, not one person's work.
  • Noise control. Hide, solo, smart branch visibility and pin-to-left, all per repository. Each resolves to a root set for a fresh walk rather than a filter over drawn rows, so lanes never draw an edge between commits that are not parent and child. The header chip always names the current scope and the gear lists what is hidden, with a way back.
  • A configurable table. Branch/Tag, Graph, Commit Message, Author, Date/Time and SHA. Right-click the header to toggle, drag to reorder, drag a divider to resize — choice, order and widths saved per repository.
  • Depth that stays readable. Past twelve lanes the pitch compresses rather than the column widening, down to a floor, so the graph can never reach the message column. Node radius follows the pitch down.

Log search#

Author, message, path, date range and diff content, composing as AND, each rendered as a chip that says exactly what is applied. Results stream as the walk finds them, and every query carries a token so starting one cancels the one before — which is what makes it safe to search on a keystroke. The path filter uses git's own simplification rule, so a merge is not listed for a change it only carried across.

File history and blame#

A file's commit timeline with rename following (--follow), beside a line-by-line blame gutter carrying author, commit and relative time. Hovering a commit in the timeline highlights every line it introduced; commit chips link back into the graph.

The reflog#

Where a ref has been — HEAD or any local branch — with three ways out of an entry: branch here, check out here, reset here, offered in that order because only the first cannot cost anything.

Changing the working copy#

  • Stage and unstage by file, hunk or line. Staged sits above Unstaged as solid rows over dashed ones, and a path appears in both when it is staged in part.
  • Discard, with a clear account of what goes away. File, hunk or everything, only on the unstaged side, each behind a confirmation whose wording says whether the file is reverted or deleted. The staged side is deliberately untouched: unstage first, which costs nothing.
  • Commit, with signing read from git. The Commit button counts staged changes, not working ones — a working copy with ten changed files and one staged must not offer to commit ten.

Diffs#

  • Unified and split views of the same data, with the choice shared across the screens that show diffs, because it is a preference about reading diffs rather than about a screen.
  • Syntax highlighting across a dozen grammars, mapped onto the active theme's own palette tokens rather than a fixed colour set.
  • Image comparison — side by side, swipe, and onion skin.
  • Binary files report a size delta rather than pretending to have lines.
  • Search inside the patch text, so a large diff can be navigated rather than scrolled.
  • Your own tools. External diff and merge tools are discovered on PATH and configured through git's own diff.tool and merge.tool keys — VS Code, Meld, Beyond Compare, KDiff3, Sublime Merge, Vimdiff and others.

Branches of work#

ThingWhat you can do
BranchesA sortable, resizable table with two-sided divergence bars; create, rename, delete, bulk-clean merged branches; checkout through git switch. Merged branches render dashed — except the one you are on.
TagsA screen of their own: create, delete, rewrite an annotated message, check out. Annotated and lightweight are told apart throughout, because the difference decides whether a message can exist.
StashesList, pop, apply, drop, and browse an entry file by file with its diff — a stash is a commit, so the Diff screen's own components render it.
WorktreesList, add (new branch, existing branch or detached), lock and unlock with a reason, remove and prune. Reachable from the tab strip and the command palette.
SubmodulesStatus, recursive init and update, URL sync, and deinit.
RemotesAdd, rename, remove and retarget, each through git remote rather than a config edit.

Rewriting and repairing#

Interactive rebase#

Plan a history rewrite and see the result before anything runs. The todo list is generated, not parsed — running git rebase -i to read the file it opens would start the rebase this screen exists to avoid. The preview is a fold of the plan, recomputed after every edit, so the plan and the picture of it cannot disagree. Rows move by drag and from the keyboard. “May conflict” is marked as a heuristic, in that word.

Conflict resolution#

Ours, the merged result and theirs side by side, with the common ancestor behind a disclosure — all four read from the index's stages, which is the whole data model. Which stages exist is the kind of conflict, and a missing side says so rather than rendering an empty pane. Three ways out of a file: take a whole side, take one marker region, or type into the merged pane, each followed by an explicit git add. Two ways out of the operation: Continue, live only once nothing is conflicted, and Abort, whose confirmation names what comes back.

Undo#

Every destructive operation confirms first and reports afterwards. Where recovery is possible the confirmation carries the actual command that brings the work back, rather than pointing vaguely at the reflog.

Working with a forge#

  • GitHub, GitLab and Bitbucket Cloud. Read pull requests, open the review workspace, comment inline, publish a review (approve, request changes, comment), reply to threads, resolve change requests, create a pull request, mark ready, merge (merge, squash or rebase), close and reopen.
  • A dedicated review workspace. A full-window view with the description rendered as markdown, collapsible panes of changed files and commits, an interactive diff with inline comment threads, and draft comments that persist in localStorage so no review work is lost to a network hiccup or a restart.
  • Reviewer and developer modes. Reviewers batch drafts into one submission; authors cannot approve their own pull requests.
  • One request per refresh. GraphQL rather than REST — REST would need a list call plus three per pull request for line counts, review decision and checks, which is ninety-one requests for thirty open ones against a budget shared with everything else the token does.
  • Four different failure sentences, because they are four different decisions for the reader: could not reach the host, rate limited and when it stops, token refused, no account connected. “Could not load” is useless to somebody deciding whether to wait or go and fix something.

Network#

Clone, fetch, push and pull from the toolbar, each watched while it runs rather than fire-and-wait. A clone shows the exact path it will land at before anything starts, refuses what can be refused without the network, parses git's own progress, and — if cancelled — removes only what it created. Spagitty never asks for a password itself: credentials go through git's own helpers, and GIT_TERMINAL_PROMPT=0 means a repository no helper can supply fails with git's own message rather than hanging on a prompt there is no terminal for.

Identity and signing#

  • Named profiles for name, email and signing key, switched from the status strip and applied to a repository or globally.
  • The scope is always a parameter, never inferred. Both values report which file they came from, the fields say which scope they are editing, and changing scope refills them rather than carrying a typed value across. A value from the system configuration or the environment is named as such rather than as a scope Spagitty writes.
  • Clearing unsets the key — git config --unset, not an empty string.
  • Signing reads what git would actually do. commit.gpgsign and its neighbours are the authority, not a Spagitty preference pretending to be that.

Attribution and standings#

Commits are credited from Co-authored-by trailers, and humans and agents are tracked separately. Agents are ranked by first-pass rate — how often their work passed without being sent back — never by commit volume, which only ranks whoever was given the most work. The agent table has no human on it: ranking the person at the keyboard against the models they are supervising turns a useful comparison into a productivity leaderboard.

The agent farm#

A goal cut into tasks, worked in parallel by the agents on your machine — one branch and one worktree each, your verification commands in the path, and a review by a second agent before anything is yours to merge. Five autonomy levels, a dependency DAG, a live activity drawer, a progress ring, per-repository standings, and AGENTS.md attached to every prompt.

It has a page of its own: the agent farm.

The delight layer#

Badges and titles for clean commits, survived rebases, recovered work and conflicts resolved — never for time spent in the application. Per repository and per actor, so a badge earned in one codebase says nothing about another. A secret badge is drawn as a slot with ??? in it rather than omitted, and the header reads n / m+?, because a total that let the secrets be worked out by arithmetic would remove the point of having any.

The Hall of Shame is a section, not a verdict: committing straight to main is acknowledged, never celebrated, gets no reward moment, cannot be equipped as a title, is left out of anything that leaves the application, and is hidden entirely at the Professional personality.

Sounds are synthesised rather than sampled — a few oscillators and a gain envelope built at play time. God mode in Settings drives the whole layer by hand so it can be checked without earning it: preview a card, fire a real event through the real rules, grant or revoke straight into the record, or operate on the whole record.

The chrome#

  • Command palette — Ctrl/Cmd+P for everything Spagitty can do. It is a registry, not a list: a feature contributes its own commands next to itself.
  • Repository tabs, including tabs onto linked worktrees.
  • A nav rail that is the only answer to “where am I” — the active item and the route are the same fact. Counts are right-aligned, and · means “not computed yet” rather than a number that would be wrong.
  • A status strip along the bottom, split into what is changing (the walk, the working copy, the last fetch) and what is merely true (commits, tags, submodules).
  • Glass window chrome — an undecorated, transparent window that draws its own corner, outline and shadows, with panes that actually refract the application behind them. How that is done, and why the usual web technique does not work here, is on themes & appearance.
  • Every panel resizes, from a registry that names each panel's variable, anchored edge and range.
  • Eight palette families in light and dark, each accented in its own hue and each contrast-checked in tests rather than by eye.

Transparency#

Show the git command behind each action adds a drawer listing what Spagitty actually ran — newest first, with the exit code and git's own stderr under anything that failed. The lines are written by the module that spawns the process, so they carry the flags the shell layer added rather than what a screen believed it asked for: that a fetch carries --prune --progress, that a force push is --force-with-lease, that reverting a merge gained -m 1 on the way down.

Reads are absent, deliberately

History walking, refs, diffs and status are answered in-process and have no command line at all. Nothing is synthesised for them and the drawer says so — inventing a git log Spagitty never ran would teach you an invocation that does not exist.
