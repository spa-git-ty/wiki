The Spagitty wiki

Spagitty

Untangle the work — yours, and your agents'.

Spagitty is a local-first desktop Git client for repositories where people and coding agents commit side by side — and it is where those agents are run: a goal, the tasks it was cut into, and the agents already installed on your machine working them in parallel, each on its own branch, in its own worktree.

This wiki is the complete documentation for Spagitty: what it does, how each screen works, how the code is arranged, and how we build and release it. It is written for three readers — someone deciding whether to use Spagitty, someone using it and looking for a specific thing, and someone reading or changing the source.

What it looks like#

Spagitty in one page#

It is a Git client first#

The commit graph, the working copy, diffs, branches, stashes, tags, the reflog, file history and blame, interactive rebase, conflict resolution, log search, clone, fetch, push and pull, remotes, worktrees, submodules, external diff and merge tools, identity profiles, commit signing, and pull requests on GitHub, GitLab and Bitbucket Cloud. Everything is on the feature reference, and every screen is on the screen reference.

And then it runs the agents#

The agent farm takes a goal, cuts it into tasks, and hands them to the coding agents already on your PATH — Claude Code, Codex, Cursor, Oh My Pi, or anything else with a command line. Each task gets its own branch and its own worktree. Verification runs your repository's commands. Review is performed by a different agent than the one that wrote the change. Neither can be skipped by an agent's own report.

The rule the farm is built around

An agent saying “done” is not done. There is no transition from an agent's own report straight to Done: verification and a peer review are in the path, and nothing in the codebase can route around them.

Nothing leaves the machine unless you ask#

There is no telemetry, no analytics, no account of ours and no server of ours in the path. Nothing in Spagitty is a model and nothing here ships a key. Repositories stay on disk; forge tokens live in the OS keychain. The whole of it is written up under privacy & security, along with the two boundaries — one process spawner, one HTTP client — that make those claims checkable rather than promised.

How we work#

Alongside the product code we keep a working record: why a change existed, what was verified, and what broke along the way. It lives in the repository under agile/ rather than in someone's head, and a test fails if the index and the tree disagree. The how we work page describes it; CI/CD & releases describes the six gates every change clears; testing says what is checked and what is deliberately not.

Status

0.x. The surface is not yet stable — a MINOR bump may break it. Every screen in the design handoff is built, the farm is built on top of them, and the release lane tags from the changelog. What remains open is named on the screen that defers it rather than left out.
