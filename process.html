How we work

The product code is one half of this repository. The other half is the working record — why a change existed, what was verified, and what broke along the way — kept in the repository rather than in someone's head.

The working record#

agile/
  items/       work items: features, tasks, bugs
  plans/       one implementation plan per work item
  testing/     test plans per work item — automated and manual sweep
  roadmap.md   the order the outstanding work is meant to be taken in

Identifiers are FEAT-###, TASK-### and BUG-###, assigned in sequence and never reused. The identifier is the join key: an item's four documents are 

agile/items/FEAT-004-branches.md
agile/plans/FEAT-004-plan.md
agile/testing/FEAT-004-automated.md
agile/testing/FEAT-004-sweep.md

and its branch is feature/FEAT-004-branches.

Backlog items — recorded but not started — carry an item document only. Their plan and testing documents are written when the work begins, since a plan written before the work is a guess rather than a record.

Status has five words, and only five#

WordMeans
DoneBuilt and merged.
FixedA bug, fixed and merged.
PartialSome of it is built and merged and some is not. The item says which.
OpenBeing worked on now.
BacklogRecorded, not started. Item document only.

Partial exists because the record had no word for it and used Backlog instead — which sent readers off to write code that was already there.

The index is checked by a test#

tools/record.test.ts runs in the ordinary suite and fails if the index and the tree disagree: a missing row, a row with no document, a status that does not match the item, a cited identifier that resolves to nothing, or a built item whose missing documents are not recorded. Drift is a test failure rather than an audit.

Branching#

Git Flow, with the work item in the branch name.

BranchFor
mainProtected. A shipping merge here publishes a release.
devProtected. Gates 1–4 run; alphas are cut from it by hand.
feature/FEAT-###-…A new capability.
task/TASK-###-…Work that is not a user-visible feature — tooling, records, refactors.
bugfix/BUG-###-…A defect.
hotfix/… · release/…Urgent fixes, and release preparation.

A pull request is the only path into a protected branch. Commits are signed off, and a changelog entry goes under ## [Unreleased] in the same change as the work.

The standing rules#

The binding rules are an amendments book shared across the author's projects and kept outside this repository, so the rules are edited once rather than copied per project. docs/AMENDMENTS.md is a pointer to it and says so explicitly — it is not a second copy, and a summary does not replace the book.

The ones that show up most in this repository, in effect:

  • The working record is required. Every change has an item, and the item's status there is authoritative.
  • A document that names a path which no longer exists is a defect, and has to be verified rather than trusted. That rule was applied to the pointer file itself, which for a while named a directory that did not exist on any machine — so the one thing it was for, telling a newcomer where the rules are, it did not do.
  • A pull request is the only path into a protected branch.
  • A release's notes are its changelog section, written with the work rather than generated afterwards.

How a change is written#

  1. An item, with what it is for and how it will be known to be done.
  2. A plan, written when the work starts.
  3. The change, on a branch named after the item, with the documentation it affects updated in the same commit — a section describing something that no longer exists is a defect.
  4. Tests, and a changelog entry under Unreleased.
  5. Gates 1 to 3 locally, then a pull request, where gates 1 to 4 are read.
  6. A sweep document, filled in with results rather than intentions.

Reasoning lives next to the code#

Module headers in this repository carry the why, not a restatement of the signature. That is a deliberate convention, and it is why the crate references on this wiki can be as specific as they are: the reasoning was already written down, in the file it belongs to.

“A search is the same revision walk the graph does, with a predicate and without lanes. It is not a second traversal of history.”

Where a decision was reversed, both halves stay — the original reasoning and what turned out to be wrong with it. The Linux rendering path is the clearest example: a workaround that fixed a blank window on some hosts cost every other host the GPU path, and the header now says both things.

Defects, kept rather than tidied away#

The record includes what broke. Not as a confession — as the useful half. A few that shaped the code:

  • A Settings chip that opened the wrong section, because eight chips fed seven branches and an {:else} catch-all hid the miss. The catch-all is gone and a test now fails if a chip is added without a branch.
  • An External Tools section themed against CSS tokens that did not exist, so every palette but one fell through to a hard-coded dark fallback — and nothing failed, because the CSS was valid.
  • A release lane that tagged a version and then could not attach its assets, because a bundle tree was uploaded whole and one icon appeared twice.
  • A release that halted rather than broke: the runner had no git identity, so git tag -a refused with fatal: empty ident name, nothing was tagged and nothing was published. The fix set the bot identity and, with it, moved the notes off generated text and onto the changelog.
  • A coverage floor the delight layer briefly dropped under, recovered by mounting the surfaces that had been left at 0% branches.
  • Eight themes wearing one accent, because “the brand runs through the UI” was applied literally. Each family accents in its own hue now, and a test fails if two ever share one.
  • A rail whose loudest pixel was a filled button offering to replace the repository you were working in — above every screen, wanted approximately never.
  • A lens that wiped the window. The glass filter's region was measured in CSS pixels and consumed as device pixels, so on any display whose ratio was not 1, most of the window stopped painting for as long as a menu was open. It is a fraction of the box now, which cannot be read in the wrong unit.
  • Two copies of a constant that drifted while doc comments on both sides claimed a test was holding them together. There was no such test. There is now.

The through-line: the leverage was real, and the verification was never optional.

Design rules that are not negotiable#

  • Standard git terminology only. fetch, push, stage, hunk, stash@{n}, pick/squash/reword/drop, ours/theirs. No invented vocabulary, no friendly renaming of git concepts.
  • Structural numbers are shared constants, never literals. If you find yourself typing 26, use the constant.
  • Never block on walking the whole history. The graph streams in windows and paints progressively.
  • Destructive actions are reversible, and the confirmation says what comes back.
  • Nothing leaves the machine. Repositories are read straight from disk; credentials go in the OS keychain.
  • Never use the Git logo or Git orange. Spagitty is independent. See brand & identity.

Where the later screens came from#

Screens 1A to 1L are the design handoff. 1M (Reflog) and 1N (Tags) came out of a gap analysis against an established client rather than the design, and they are numbered after the handoff's run rather than inserted into it — so a screen code still says where that screen came from. 1P (Badges) came from neither. That analysis is kept in the repository alongside a reference document recording what the commit graph deliberately will not do: no dragging commits, no inline message editing, no manual lane layout, no independent graph zoom.
