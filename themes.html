Using Spagitty

Themes & appearance

Eight palette families, each in light and dark, each accented in its own hue and each contrast checked in tests rather than by eye. Plus the glass the chrome is made of, and two independent dials for how big everything is.

The palettes#

Settings → Appearance is the only place the theme is set. Each family is shown as its own four colours in the mode currently on — a light preview of a theme about to be used in the dark is a preview of something nobody will see.

Each variant is named the way its own family names it, rather than renamed to “light” and “dark”.

They are data, not stylesheets#

The palettes live in src/lib/themes.ts and are applied to <html> as custom properties. Sixteen :root[data-theme=…] blocks would be the same fourteen tokens written sixteen times with nothing able to check them; as data they are tested — and what is tested is the thing that matters about a colour, which is whether it can be read.

themes.test.ts computes WCAG contrast for all sixteen, compositing the translucent tokens over what actually shows through them, and holds ordinary text to 4.5:1 and secondary text, the accent and every lane colour to 3:1. Three published upstream values failed that and were adjusted rather than shipped: Latte's pink, peach and yellow are invisible as lanes on its own background, and Tokyo Night Day's blue cannot carry white text. Each departure is marked where it is made.

Every family accents in its own hue#

For a while the palettes all wore the brand amber — which put one colour on seven palettes built around a different one: an amber primary button in the middle of Dracula's purples, and a brown that read as muddy on every light background. “The brand runs through the UI” had been applied literally. Each family accents with a colour of its own now, contrast-checked the same way, and a test fails if two families ever share one.

Switching is cheap

Changing the theme writes custom properties and nothing else — no component re-render, no stylesheet swap. src/app.css carries the default family's two palettes as the boot values, what paints before any JavaScript runs, and nothing more: editing a colour there changes the first frame and not the theme.

The glass#

Every bar, rail, menu and dialog is a frosted pane, and the panes that float — menus and dialogs — also refract: the application behind them is pushed outward toward each rim, and the colour splits a little where the bend is sharpest. Thick glass bends light.

It is not done the way the web does it#

backdrop-filter: url(#filter) is what every published recreation of this effect uses, and WebKitGTK renders nothing for it: the declaration parses, CSS.supports answers yes, and the pane comes out identical to one with no filter at all.

So the filter goes on the other side of the glass — an ordinary filter on the application underneath, displacing it in a ring the exact shape of each pane. What bends around a menu is the actual commit list, actually displaced.

Two consequences are visible in the markup:

  • The filtered element is .lens, a wrapper inside .app. .app carries the window's outline and cast shadow, both drawn outside its border box, and a filter clips to that box — so filtering .app would cut the window's own edge off for as long as a menu was open.
  • A pane cannot be inside what it bends, so a menu raised deep in a screen is moved to a window-sized stage of its own.

The region is a fraction, never a measurement#

The filter covers 0 0 1 1 in object-bounding-box units. It used to be the element's measured width and height in user-space units — CSS pixels, which WebKitGTK consumes as device pixels, so on any display whose ratio is not 1 the region covered 1 / devicePixelRatio of the window and the rest of it simply stopped painting for as long as a menu was open. A fraction cannot be read in the wrong unit.

Worth knowing before diagnosing anything here

The compositor's monitor scale is not the webview's ratio. Hyprland reports scale: 1 on a display where WebKitGTK reports 1.3636.

The arithmetic lives in src/lib/ui/liquidGlassMaps.ts and is tested without a window; the measuring and the registry are in liquidGlass.ts, which does nothing at all when there is no .lens to filter — which is every component test.

Two dials for size#

DialRangeWhat it scales
Text size90–130% The type tokens and the commit-row pitch, and nothing else. The “the font is too small” dial: chrome, gutters and lane geometry keep their proportions, so the window holds the same shape and only the words get bigger. The row pitch has to follow the type, or a 17px line would be clipped by a 26px row.
Interface zoom100–200% Everything — type, structural metrics, radii, lane geometry. The “this display is too dense” dial.

They compose: effective type is base × zoom × text, effective structure is base × zoom. Both live in localStorage alongside the theme rather than with the settings the backend owns, and for the same reason — they have to be applied on the first frame, and the boot path cannot wait on a command to find out how big the window's text is.

Personality and sound#

The delight layer has a register control, because not everybody wants a badge to interrupt them.

PersonalityEffect
ProfessionalNo reward moments, no titles, no Hall of Shame. Badges are still recorded and still visible on their own screen.
BalancedThe default. Reward moments for real unlocks; nothing loud.
Full SpagittyThe whole register, jokes included.

Sounds are off by default and synthesised rather than sampled — every noise Spagitty makes is a few oscillators and a gain envelope built at play time. Nothing in the delight layer can fail a git operation: every call site into it is discarded, and recording swallows its own failure.

Structural numbers have one home#

There is no height: 26px in any component and no second 26 anywhere in the frontend. Structural metrics live in src/lib/metrics.ts and are published as CSS custom properties. The commit-row pitch is defined twice on purpose — once there and once in the Rust graph module, which describes lane elbows in row units — and a test reads the TypeScript file from Rust and fails with both values named if they ever disagree. See testing.
